1. Mental model tổng thể

Azure Subscription └── Resource Group ├── AKS │ ├── Control Plane (managed by Azure) │ ├── Node Pool │ │ └── VMSS / Nodes │ ├── Deployment │ │ └── ReplicaSet │ │ └── Pods │ ├── Service │ ├── EndpointSlice │ └── Ingress ├── VNet / Subnet / NSG / Route Table ├── Load Balancer / App Gateway / F5 path ├── ACR ├── Key Vault ├── Managed Identity ├── Log Analytics / Azure Monitor └── Private DNS / Private Endpoint
Nguyên tắc TA: Khi có lỗi, đừng hỏi “Kubernetes có lỗi không?” mà hỏi “lỗi nằm ở layer nào?”. Mỗi layer có symptom, command kiểm tra và team chịu trách nhiệm khác nhau.

2. P0 - bắt buộc phải chắc

P0.1 AKS Architecture: Control Plane ↔ Node Pool ↔ Node

Nguyên nhân cần học: rất nhiều incident application nhìn giống lỗi Pod nhưng nguyên nhân thật là Node, Node Pool, VMSS hoặc capacity.

Kubernetes side

  • API Server: điểm vào cho kubectl.
  • Scheduler: chọn Node cho Pod.
  • Controller Manager: giữ trạng thái thực tế giống desired state.
  • etcd: lưu cluster state.
  • kubelet: agent trên từng Node.

Azure side

  • AKS resource: Microsoft.ContainerService/managedClusters.
  • Node Pool: nhóm compute cùng VM size / OS.
  • VMSS: nơi Azure cấp VM instances cho worker nodes.
  • VNet/Subnet: nơi node network hoạt động.
az aks show -g <rg> -n <aks> -o jsonc
az aks nodepool list -g <rg> --cluster-name <aks> -o table
kubectl get nodes -o wide
kubectl describe node <node>

Ví dụ thực tế: Pod Pending dù Deployment đúng

Triệu chứng: Deployment desired=5 nhưng chỉ có 3 Pod Running, 2 Pod Pending.

Cách kiểm tra:

kubectl describe pod <pending-pod> -n app

Output điển hình:

0/3 nodes are available:
2 Insufficient memory,
1 node(s) had untolerated taint.

Kết luận: Không phải application code. Cần kiểm tra requests/limits, node taints, nodepool capacity hoặc Cluster Autoscaler.

P0.2 Deployment → ReplicaSet → Pod

Deployment ↓ desired state / rollout / replicas ReplicaSet ↓ giữ đúng số lượng Pods ↓ Containers ↓ .NET process
ObjectCâu hỏi cần trả lờiCommand chính
DeploymentApp muốn chạy bao nhiêu replica, image nào, strategy nào?kubectl describe deployment
ReplicaSetDesired/Current/Ready có khớp không?kubectl get rs
PodPod nằm node nào, status gì, restart bao nhiêu?kubectl get pod -o wide
ContainerProcess có crash, OOM, exception?kubectl logs

Ví dụ rollout lỗi

kubectl rollout status deployment/order-api -n app
kubectl rollout history deployment/order-api -n app
kubectl describe deployment order-api -n app

Nếu bản mới dùng image tag sai, ReplicaSet mới sẽ được tạo nhưng Pod sẽ ImagePullBackOff. Khi đó rollback có thể là action phù hợp hơn restart.

P0.4 Service → EndpointSlice → Pod

Client trong cluster ↓ Service (stable DNS / ClusterIP) ↓ selector EndpointSlice ↓ Pod IP : targetPort

Điểm cần nhớ: Service không “chứa” Pod. Service dùng selector để tìm Pod labels; EndpointSlice phản ánh backend thực tế.

Ví dụ selector sai

# Service
selector:
  app: order-api

# Pod labels
labels:
  app: orders-api

Kết quả: Pod Running, Service tồn tại nhưng EndpointSlice rỗng.

kubectl describe svc order-api -n app
kubectl get endpointslice -n app
kubectl get pods -n app --show-labels

P0.5 Readiness / Liveness / Startup Probe

ProbeMục đíchKhi fail
ReadinessPod có nhận traffic được chưa?Pod bị loại khỏi backend traffic
LivenessApp còn sống không?Container restart
StartupApp startup chậm đã xong chưa?Tránh liveness giết app quá sớm

Ví dụ .NET

readinessProbe:
  httpGet:
    path: /health/ready
    port: 8080

livenessProbe:
  httpGet:
    path: /health/live
    port: 8080

App process vẫn chạy nhưng SQL connection fail → readiness fail → Pod Running nhưng READY 0/1 → Service không route traffic.

P0.6 Ingress + DNS + Load Balancer

Client ↓ DNS ↓ F5 / Azure LB / App Gateway ↓ Ingress Controller ↓ Ingress rule ↓ Service ↓ EndpointSlice ↓ Pod

Ví dụ URL trả 404 dù Pod healthy

  • DNS resolve đúng.
  • TLS handshake thành công.
  • Ingress host cấu hình api.internal.
  • User gọi api.ceva.internal.

Kết quả: request tới Ingress Controller nhưng không match host rule → 404 mặc dù backend hoàn toàn healthy.

nslookup api.ceva.internal
curl -vk https://api.ceva.internal
kubectl get ingress -A
kubectl describe ingress <name> -n <ns>

P0.7 Logs + Events + Historical monitoring

Ba nguồn evidence:

  1. kubectl logs: log hiện tại.
  2. kubectl get events: lifecycle/scheduling/probe/image errors.
  3. Azure Monitor / Log Analytics: historical và cross-pod/cross-node.
kubectl logs <pod> -n <ns>
kubectl logs <pod> -n <ns> --previous
kubectl get events -n <ns> --sort-by=.lastTimestamp

3. P1 - cần chắc để troubleshoot production

P1.1 Node / Scheduling / Taints / Tolerations

Scheduler chọn Node dựa trên request resource, labels, nodeSelector, affinity, taints/tolerations và các constraint khác.

kubectl describe node <node>
kubectl describe pod <pod>

Ví dụ agent Windows: nodepool Windows có taint workload=windows:NoSchedule. Pod agent thiếu toleration → Pending dù node vẫn Ready.

P1.2 Requests / Limits ↔ VM sizing

resources:
  requests:
    cpu: 500m
    memory: 512Mi
  limits:
    cpu: "1"
    memory: 1Gi
Khái niệmÝ nghĩa
requestsScheduler dùng để tính chỗ đặt Pod
limitsTrần tài nguyên runtime

Case 1: Pod cần request 8Gi nhưng Node chỉ còn 4Gi → Pending.

Case 2: App dùng 1.3Gi trong khi limit 1Gi → OOMKilled.

P1.3 ACR + Image lifecycle

Azure DevOps ↓ docker build ACR repository:tag ↓ image pull AKS kubelet identity ↓ Pod
az acr repository list -n <acr> -o table
az acr repository show-tags -n <acr> --repository <repo> -o table

Case thực tế: Deployment trỏ tag 20260318.1, ACR không có tag hoặc kubelet identity thiếu AcrPull → ImagePullBackOff.

P1.4 Managed Identity + Azure RBAC

Application / AKS identity ↓ Azure RBAC role ↓ Scope ↓ Key Vault / ACR / Storage / other resource

Công thức phải nhớ: Identity + Role + Scope.

Identity đúng nhưng role sai → 403. Role đúng nhưng scope gán nhầm resource → 403. Network sai → timeout/DNS error chứ không phải authorization error.

P1.6 HPA + Cluster Autoscaler

Traffic ↑ ↓ CPU / custom metric ↑ ↓ HPA ↓ Pods 3 → 8 ↓ nếu thiếu node capacity Cluster Autoscaler ↓ Node Pool / VMSS scale out
kubectl get hpa -A
kubectl describe hpa <name> -n <ns>
az aks nodepool show -g <rg> --cluster-name <aks> -n <pool> -o jsonc

P1.7 Helm + Azure DevOps

Azure DevOps Pipeline ↓ Service Connection ↓ Helm chart + values ↓ Rendered manifests ↓ AKS resources
helm list -A
helm history <release> -n <ns>
helm get values <release> -n <ns>
helm get manifest <release> -n <ns>

Case: Pipeline green nhưng app sai config → so sánh pipeline variables → values.yaml → rendered manifest → actual Deployment/ConfigMap.

P1.8 Azure DevOps Service Connection

User account và pipeline identity là hai principal khác nhau.

Your admin account ≠ Pipeline Service Connection Identity

Vì vậy việc anh có Contributor không có nghĩa pipeline cũng có Contributor.

Case: Pipeline gọi Azure API trả AuthorizationFailed; cần kiểm tra principal của service connection và role assignment scope.

P1.9 RBAC + PIM

Có hai authorization layer:

Azure PIM / Azure RBAC ↓ AKS resource access / get credentials ↓ Kubernetes API ↓ Kubernetes RBAC ↓ pods / deployments / secrets ...

Do đó có thể activate Contributor xong nhưng kubectl get pods vẫn Forbidden.

Ngày 1 — AKS Architecture, Control Plane, Node, kubectl P0
Mục tiêu: hiểu Kubernetes là một hệ thống điều phối container, biết Control Plane làm gì, Node làm gì, và kubectl thực sự đang nói chuyện với thành phần nào.

1. Kubernetes là gì?

Kubernetes (K8s) là nền tảng orchestration cho container. Nó giải quyết các bài toán mà Docker đơn lẻ không giải quyết tốt:
  • Container chết thì ai tạo lại?
  • Cần 10 instance của API thì ai giữ đúng 10 instance?
  • Deploy version mới mà không downtime thế nào?
  • Traffic phân phối vào các container nào?
  • Node chết thì workload chuyển sang đâu?
Docker vs Kubernetes:
DockerKubernetes
Chạy container trên một hostĐiều phối container trên nhiều node
docker runDeployment/Pod/Service
Tự quản restart/scaleSelf-healing, scaling, rollout
Phù hợp local/small setupPhù hợp cluster/production

2. Control Plane là gì?

Control Plane là “bộ não” của cluster. Nó không phải nơi application business của anh chạy; nó là nơi Kubernetes quyết định cluster phải trông như thế nào.
kubectl / Pipeline ↓ API Server ↓ etcd ← lưu desired/current state ↓ Controller Manager ↓ Scheduler ↓ Worker Node / kubelet ↓ Pod / Container

3. Từng thành phần Control Plane

3A. Nhiệm vụ/chức năng real-world của từng thành phần

API Server — “cổng điều hành” của Kubernetes
  • Nhiệm vụ: nhận mọi request đọc/ghi cluster state.
  • Chức năng: authentication, authorization, admission checks, validate request rồi đọc/ghi state.
  • Ai gọi nó? kubectl, Helm, Azure DevOps pipeline, controllers, operators.
  • Nếu API Server có vấn đề: kubectl/Helm/pipeline không thao tác cluster được, dù một số Pods đang chạy vẫn có thể tiếp tục chạy.
Ví dụ đời thực: API Server giống quầy tiếp nhận lệnh trong trung tâm điều hành. Không ai được đi thẳng vào kho dữ liệu etcd; mọi yêu cầu đều qua quầy này.
etcd — “database trạng thái” của cluster
  • Nhiệm vụ: lưu desired state và metadata quan trọng của Kubernetes.
  • Ví dụ lưu: Deployment replicas=3, Service selector, Secret object, ConfigMap, Node registrations.
  • Không dùng để: lưu database business như đơn hàng, khách hàng, shipment.
Ví dụ: anh khai báo Deployment có 3 replicas. Con số “3” phải được lưu ở đâu để controller biết mà reconcile? → etcd.
Controller Manager — “người giám sát desired state”
  • Nhiệm vụ: liên tục kiểm tra actual state có lệch desired state không.
  • Ví dụ: desired=3 Pods, actual=2 → controller kích hoạt việc tạo Pod mới.
  • Ý nghĩa production: self-healing của Kubernetes đến từ các reconciliation loops kiểu này.
Ví dụ đời thực: giống quản đốc nhà máy thấy kế hoạch cần 3 dây chuyền chạy nhưng hiện chỉ còn 2 → yêu cầu mở lại dây chuyền thứ 3.
Scheduler — “bộ phận phân chỗ”
  • Nhiệm vụ: chọn Node phù hợp cho Pod mới.
  • Xem xét: CPU/memory requests, node labels, nodeSelector, taints/tolerations, affinity, topology.
  • Không làm: không tự start container; nó chỉ quyết định Pod sẽ chạy ở Node nào.
Ví dụ: Pod Windows agent cần Windows node + đủ 8Gi memory. Scheduler sẽ không đặt nó lên Linux node hoặc node chỉ còn 4Gi.
kubelet — “agent quản lý workload trên từng Node”
  • Nhiệm vụ: nhận PodSpec đã được assign cho Node rồi đảm bảo containers chạy đúng.
  • Làm việc với: container runtime, volumes, probes, container status.
  • Nếu kubelet lỗi: Node có thể chuyển NotReady, Pods trên đó không còn được quản lý đúng.
Ví dụ: Scheduler nói “Pod A chạy trên Node 2”. Kubelet ở Node 2 mới là thành phần thực sự kéo image và yêu cầu runtime start container.
Container Runtime — “máy thực thi container”
  • Nhiệm vụ: pull image, create/start/stop container.
  • Ví dụ: containerd là runtime phổ biến trong Kubernetes hiện đại.
Ví dụ: kubelet là quản lý ca; container runtime là máy móc thật sự chạy chương trình.
Thành phầnKhái niệmVí dụ thực tế
API Server Gateway chính của Kubernetes API. Mọi thao tác kubectl, Helm, operator đều đi qua đây. Anh chạy kubectl get pods → kubectl gửi HTTPS request tới API Server.
etcd Distributed key-value store lưu state của cluster. Deployment muốn 3 replicas, Service selector, ConfigMap... đều là state cần lưu.
Controller Manager Chạy các controller liên tục so sánh desired state với actual state. Desired=3 Pod nhưng actual=2 → controller tạo thêm 1 Pod.
Scheduler Chọn Node phù hợp cho Pod chưa được schedule. Pod cần 4GB RAM → Scheduler chọn node còn đủ memory và thỏa taints/labels.
Cách hình dung: Control Plane giống “ban điều hành”. Node giống “nhà máy”. Deployment là “kế hoạch sản xuất”. Pod là “đơn vị sản xuất thực tế”.

4. AKS khác Kubernetes tự dựng thế nào?

AKS (Azure Kubernetes Service) là Kubernetes managed bởi Azure. Azure quản lý Control Plane; anh chủ yếu quản lý node pool, workload, network, identity, monitoring.

Azure Subscription └── Resource Group └── AKS ├── Control Plane (Azure manages) └── Node Pools └── VMSS └── Kubernetes Nodes

5. Node Pool / VMSS / Node là gì?

Node Pool: nhóm worker nodes cùng OS/VM size/config.
VMSS: Azure Virtual Machine Scale Set đứng phía dưới node pool.
Node: worker machine mà Kubernetes nhìn thấy.
Ví dụ: Cluster có Linux node pool cho APIs và Windows node pool cho build agents. 
nodepool-linux → Standard_D4s_v5 → 3 Linux nodes
nodepool-win   → Standard_D8s_v5 → 2 Windows nodes
API Linux không thể tự nhiên schedule sang Windows node nếu image/constraints không phù hợp.

6. kubectl là gì?

kubectl — cụ thể dùng để làm gì?
  • Đọc trạng thái: get, describe.
  • Xem log: logs.
  • Debug: exec, port-forward.
  • Thay đổi resource: apply, scale, rollout, delete.
  • Kiểm tra quyền: auth can-i.
Ví dụ: Azure Portal cho anh giao diện nhìn cluster; kubectl cho anh thao tác trực tiếp Kubernetes API và thường nhanh/chính xác hơn khi troubleshoot.
kubectl là CLI client của Kubernetes. Nó không phải Kubernetes server; nó chỉ là công cụ gửi request đến Kubernetes API Server. 
kubectl get pods
kubectl describe pod my-pod
kubectl logs my-pod
kubectl ↓ đọc kubeconfig cluster endpoint + certificate + identity ↓ HTTPS Kubernetes API Server

7. kubeconfig là gì?

Kubeconfig lưu thông tin cluster, context, user/credential. Khi dùng AKS:

az aks get-credentials -g <rg> -n <aks>
kubectl config current-context
kubectl config get-contexts
Security basic — Authentication vs Authorization:
Authentication = “Anh là ai?”. Authorization = “Anh được làm gì?”.
Anh có thể authenticate được vào AKS nhưng vẫn bị Forbidden nếu Kubernetes RBAC không cho quyền.
Network basic: kubectl cần kết nối TCP/443 đến Kubernetes API Server. Private AKS còn phụ thuộc corporate network/VPN/ExpressRoute/private DNS.

Ngày 2 — Deployment, ReplicaSet, Pod, Container, Namespace P0
Mục tiêu: hiểu object hierarchy và biết object nào chịu trách nhiệm chuyện gì.

1. Namespace là gì?

Namespace là logical boundary trong cluster để nhóm resource. Nó giống “folder/tenant nhỏ” chứ không phải VM riêng. 
kubectl get ns
kubectl get pods -n app-tom

Thực tế công ty có thể tách theo app/environment/team: tom-pr, sonarqube, monitoring.

2. Pod là gì?

Pod là deployable unit nhỏ nhất của Kubernetes. Thường một Pod chứa một application container, đôi khi có sidecar.
Pod ├── app container └── optional sidecar shared network namespace + volumes

Các container trong cùng Pod có thể gọi nhau qua localhost.

Quan trọng: Pod là disposable. Pod mới có thể đổi tên, đổi IP. Đừng thiết kế application phụ thuộc vào Pod IP cố định.

3. ReplicaSet là gì?

ReplicaSet giữ đúng số lượng Pod theo selector.

Desired replicas=3. Một Pod chết → ReplicaSet tạo Pod mới để actual trở về 3.

4. Deployment là gì?

Deployment quản lý ReplicaSet và cung cấp rolling update, rollback, scaling, declarative desired state.

Deployment v2 ↓ creates ReplicaSet v2 ↓ Pods v2 Deployment vẫn giữ ReplicaSet v1 trong history để rollback

5. Rolling Update hoạt động thế nào?

Thay vì stop toàn bộ v1 rồi start v2, Deployment thay dần từng Pod.

v1 v1 v1
↓
v2 v1 v1
↓
v2 v2 v1
↓
v2 v2 v2

6. kubectl apply là gì?

kubectl apply -f gửi YAML desired state vào API Server. Kubernetes cố reconcile actual state về desired state.

Declarative vs Imperative:
ImperativeDeclarative
kubectl scale ...YAML/Helm values mô tả desired state
Nhanh cho debugPhù hợp GitOps/pipeline/production

Ngày 3 — Pod Lifecycle, Logs, Events, CrashLoop, OOMKilled P0
Mục tiêu: nhìn Pod status và suy ra nhóm nguyên nhân trước khi đọc log.

1. Pod lifecycle

Các phase phổ biến: Pending, Running, Succeeded, Failed. Các trạng thái như CrashLoopBackOff/ImagePullBackOff thường nằm ở container state/reason.

3. CrashLoopBackOff

Kubernetes start container → container crash → restart → crash liên tục → backoff tăng dần.

.NET app khởi động và đọc connection string nhưng Secret thiếu: 
Unhandled exception:
System.InvalidOperationException:
Connection string 'MainDb' was not found.
Không nên chỉ restart; phải kiểm tra env/Secret/ConfigMap.

4. OOMKilled

OOM = Out Of Memory. Container vượt memory limit và bị kernel kill.
Last State:
  Terminated:
    Reason: OOMKilled
    Exit Code: 137
Root cause không nhất thiết chỉ là limit thấp. Có thể memory leak, cache tăng vô hạn, batch workload lớn, traffic spike.

5. Pending

Pod chưa được schedule hoặc chưa sẵn sàng start. Xem Events trước.

0/5 nodes are available:
3 Insufficient memory,
2 node(s) had untolerated taint.

6. ImagePullBackOff

Node không pull được image. Các hướng: image/tag không tồn tại, ACR auth, DNS/network, firewall/private endpoint.

Network basic: Pull image là outbound traffic từ node/kubelet tới ACR endpoint. DNS + HTTPS 443 + identity đều phải hoạt động.
Security basic: ACR private thường dựa trên managed identity/AcrPull thay vì username/password.

Ngày 4 — Service, ClusterIP, DNS, EndpointSlice, Port/TargetPort P0
Mục tiêu: hiểu traffic nội bộ cluster và vì sao không gọi trực tiếp Pod IP.

1. Service là gì?

1A. Nhiệm vụ thực tế của Service

Service — “địa chỉ ổn định trước một nhóm Pods”
  • Nhiệm vụ 1: che giấu việc Pod IP thay đổi.
  • Nhiệm vụ 2: cung cấp DNS/ClusterIP ổn định.
  • Nhiệm vụ 3: phân phối traffic tới nhiều healthy endpoints.
  • Nhiệm vụ 4: tách client khỏi lifecycle của Pods.
Ví dụ: Frontend không gọi 10.244.1.5 vì Pod này có thể chết. Frontend gọi http://order-api; Service tự route sang Pod hiện đang sống.
EndpointSlice — “danh bạ backend hiện tại”
  • Nhiệm vụ: ghi danh sách IP/port của endpoints backend.
  • Liên hệ Service: Service là abstraction; EndpointSlice cho anh thấy backend cụ thể.
  • Troubleshooting: Service có nhưng EndpointSlice rỗng → selector/readiness thường là nơi cần xem.
CoreDNS — “DNS server nội bộ của cluster”
  • Nhiệm vụ: resolve Service name, ví dụ order-api.app.svc.cluster.local.
  • Nếu lỗi: Pods có thể không gọi được nhau bằng tên dù IP/network vẫn tồn tại.
Ví dụ: API gọi Redis qua redis-master. Nếu CoreDNS có issue, app báo name resolution error, không phải Redis port issue.

Service cung cấp stable virtual endpoint cho một nhóm Pods. Pods thay đổi nhưng Service name/ClusterIP giữ ổn định.

2. ClusterIP là gì?

Virtual IP dùng bên trong cluster. Client thường gọi qua DNS name thay vì IP.

http://order-api
http://order-api.app.svc.cluster.local

3. Kubernetes DNS

CoreDNS cung cấp name resolution trong cluster. Service name được resolve về ClusterIP.

DNS basic: DNS chỉ giải quyết hostname → IP. DNS resolve thành công không có nghĩa TCP/HTTP backend hoạt động.

4. port vs targetPort

Service port:       80
Service targetPort: 8080
Container listens:  8080

Client gọi Service:80; Service forward tới Pod:8080.

5. Selector / Labels

Service tìm Pod dựa trên labels.

selector:
  app: order-api

6. EndpointSlice là gì?

EndpointSlice lưu danh sách backend endpoints mà Service có thể route đến. Đây là điểm kiểm tra rất mạnh khi troubleshoot.

Service tồn tại nhưng: 
Endpoints: <none>
Kiểm tra selector/labels và Pod readiness.

Ngày 5 — Health Probes, Application Health, Failure Semantics P0
Mục tiêu: thiết kế và troubleshoot probe đúng, tránh “self-healing” biến thành “self-killing”.

1. Readiness

Trả lời: Pod có sẵn sàng nhận traffic chưa?

Fail readiness không restart container; Pod chỉ bị loại khỏi traffic.

2. Liveness

Trả lời: process còn sống/healthy không? Fail liveness có thể restart container.

3. Startup

Dùng cho app startup lâu; trong thời gian startup probe chưa pass, liveness/readiness chưa đánh giá theo cách gây restart quá sớm.

4. HTTP/TCP/Exec probes

LoạiVí dụ
HTTPGET /health/ready
TCPPort 8080 có accept connection không?
ExecChạy command trong container
Case: API phụ thuộc SQL. SQL down 20 giây. Nếu readiness check SQL thì Pod tạm ngưng nhận traffic. Nếu liveness cũng check SQL và fail → toàn bộ Pods có thể restart đồng loạt, làm incident nặng hơn.
Ôn network: TCP probe chỉ biết port mở; HTTP probe biết thêm application response/status code.
Security: health endpoint không nên trả secret/config nội bộ. Có thể expose minimal status mà không lộ dependency detail ra public route.

5. Timing parameters

  • initialDelaySeconds
  • periodSeconds
  • timeoutSeconds
  • failureThreshold
Đọc probe config một app thật và tính mất bao lâu từ khi lỗi tới khi readiness/liveness effect xảy ra.
Ngày 6 — Ingress, Ingress Controller, DNS, TLS, SNI, Load Balancer P0
Mục tiêu: hiểu từ URL bên ngoài vào đến Service trong cluster.

1. Ingress là gì?

Ingress là Kubernetes resource mô tả HTTP/HTTPS routing rules: hostname/path → Service.

2. Ingress Controller là gì?

2A. Ingress Controller thực sự làm gì?

Ingress Controller — “reverse proxy/router chạy thật”
  • Nhiệm vụ 1: watch Kubernetes API để đọc các Ingress resources.
  • Nhiệm vụ 2: build/update routing configuration tương ứng.
  • Nhiệm vụ 3: nhận HTTP/HTTPS traffic từ Load Balancer/F5/App Gateway.
  • Nhiệm vụ 4: match hostname/path và forward request tới đúng Service.
  • Nhiệm vụ 5: tùy controller, có thể terminate TLS, redirect HTTP→HTTPS, rewrite path, set headers, rate limit.
Ví dụ: Anh có rule orders.ceva.internal/api → orders-service:80. Ingress resource chỉ “ghi luật”. NGINX Ingress Controller mới là process nhận request thật, đọc Host header/path rồi proxy request sang Service.
Ingress vs Ingress Controller vs Load Balancer:
Thành phầnBản chấtReal-world role
IngressKubernetes config objectBảng routing rules
Ingress ControllerRunning software/proxyThực thi routing rules
Load Balancer/F5/AppGWNetwork entry pointĐưa traffic từ ngoài tới controller/backend
Case thực tế: Ingress YAML đúng nhưng controller Pod crash.
Kết quả: rule vẫn nhìn thấy bằng kubectl get ingress, nhưng traffic không được xử lý đúng vì thành phần thực thi đang hỏng.

Ingress chỉ là config. Cần một controller (NGINX, Application Gateway Ingress Controller, Traefik...) thực sự đọc config và xử lý traffic.

Ví dụ dễ hình dung: Ingress = bảng quy tắc giao thông. Ingress Controller = cảnh sát/thiết bị thực thi quy tắc đó.

3. Host/path routing

orders.ceva.internal/api  → orders-api-service
orders.ceva.internal/ui   → orders-ui-service

4. DNS là gì?

DNS chuyển hostname thành IP. Có thể là corporate DNS, Azure Private DNS, public DNS.

5. TLS là gì?

TLS bảo vệ kết nối: encryption + server identity qua certificate.

6. SNI là gì?

Server Name Indication cho phép client gửi hostname trong TLS handshake để một IP có thể phục vụ nhiều certificate/site.

F5/Ingress dùng chung IP cho nhiều hostname. Nếu test bằng IP nhưng không giữ đúng hostname/SNI, certificate/backend có thể khác.

7. Load Balancer vs Ingress

Load BalancerIngress
Thường Layer 4 hoặc cloud LBHTTP/HTTPS routing Layer 7
IP:PortHost/path/header aware
Ôn OSI: DNS ở application layer; TCP ở Layer 4; TLS nằm trên TCP; HTTP là Layer 7. Troubleshoot nên đi theo layer.

1. Container image là gì?

2A. ACR thực sự làm gì trong flow production?

  • Nhiệm vụ: lưu container images theo repository/tag/digest.
  • Không chạy container: ACR chỉ lưu/phân phối image; AKS Node mới chạy image.

Ngày 11 — Managed Identity, Azure RBAC, Key Vault, Private Endpoint, DNS P1
Mục tiêu: hiểu authentication/authorization/network path của workload tới Azure resource.

1. Managed Identity là gì?

1A. Managed Identity giải quyết bài toán gì?

Managed Identity — “Azure-managed identity cho workload”
  • Nhiệm vụ: cho workload lấy Azure AD/Entra token mà không phải quản lý client secret lâu dài.
  • Dùng để: gọi Key Vault, Storage, Service Bus, ACR... tùy role.
  • Không tự cấp quyền: có identity chưa đủ; vẫn cần RBAC role đúng scope.
Ví dụ: Pod cần đọc Key Vault. Thay vì nhét client secret vào env, workload dùng managed identity/workload identity để xin token rồi gọi Key Vault.
Key Vault — “kho secret/key/certificate tập trung”
  • Nhiệm vụ: lưu và kiểm soát access tới secrets/keys/certificates.
  • Giá trị: centralize secret management, auditing, rotation, RBAC.
  • Không thay thế ConfigMap: non-sensitive config không nhất thiết đưa vào Key Vault.
Private Endpoint — “private NIC cho PaaS”
  • Nhiệm vụ: làm Azure PaaS service xuất hiện bằng private IP trong VNet.
  • Đi kèm: Private DNS để hostname resolve về private IP.

Identity do Azure quản lý cho resource/workload, giúp lấy token mà không phải lưu client secret dài hạn.

2. Azure RBAC là gì?

Role Based Access Control xác định identity nào được action gì trên scope nào.

Công thức: Principal/Identity + Role + Scope.

3. Scope hierarchy

Management Group ↓ Subscription ↓ Resource Group ↓ Resource

Role ở scope cao có thể inherit xuống scope thấp.

4. Key Vault là gì?

Azure service lưu secrets, keys, certificates.

5. Private Endpoint là gì?

Đưa một private IP của Azure PaaS vào VNet, để traffic không cần đi public endpoint.

6. Private DNS

Hostname PaaS cần resolve về private IP đúng khi dùng Private Endpoint.

Case: app gọi Key Vault timeout.
Nếu 403 → nghĩ identity/RBAC.

Ôn OSI nhanh:
Layer 3 = IP/routing (VNet, route).
Layer 4 = TCP/UDP/port (NSG, Load Balancer thường xử lý mạnh ở đây).
Layer 7 = HTTP/host/path (Ingress Controller, App Gateway).

VNet là private network logical trong Azure; subnet chia VNet thành các vùng IP nhỏ hơn.

2. NSG

Network Security Group là allow/deny rules ở Layer 3/4 dựa trên source/destination IP, protocol, port.

3. Route Table / UDR

Quyết định traffic đi next hop nào: Internet, Virtual Appliance, Virtual Network Gateway...

4. CNI là gì?

Container Network Interface plugin giúp Pod được cấp network và communicate trong cluster/network.

7. End-to-End mock incident

Symptom: https://orders-dev... trả 503.
  1. DNS: resolve đúng LB IP.
  2. TCP: port 443 reachable.
  3. TLS: certificate/SNI OK.
  4. Ingress: host/path match.
  5. Service: tồn tại, selector đúng.
  6. EndpointSlice: không có ready endpoint.
  7. Pod: Running nhưng READY 0/1.
  8. Probe: readiness 503 vì SQL timeout.
  9. DNS trong Pod: SQL hostname resolve sai public IP.
  10. Root cause: Private DNS link/config sai.

5. Incident playbook thực tế

Playbook A - URL không truy cập được

1. nslookup hostname
2. Test-NetConnection hostname -Port 443
3. curl -vk https://hostname
4. kubectl describe ingress
5. kubectl describe svc
6. kubectl get endpointslice
7. kubectl get pod -o wide
8. kubectl logs / logs --previous
9. check dependency: SQL / Redis / Kafka / external API

Playbook B - Pod restart liên tục

kubectl get pod
kubectl describe pod
kubectl logs <pod>
kubectl logs <pod> --previous
kubectl get events

Phân loại: app exception / OOMKilled / probe fail / secret-config / dependency unavailable.

Playbook C - Pipeline deploy fail

1. Identify service connection principal
2. Check Azure RBAC scope
3. Check AKS credentials / K8s RBAC
4. Check Helm release history
5. Check rendered values/manifests
6. Check ACR image tag exists

Playbook D - Pod healthy nhưng không access Key Vault/SQL

1. Identity đúng?
2. RBAC role đúng?
3. Scope đúng?
4. DNS resolve private endpoint?
5. Route/NSG cho phép?
6. TLS/port reachable?
7. App config đúng?
