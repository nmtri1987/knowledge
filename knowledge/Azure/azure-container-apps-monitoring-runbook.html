Azure Container Apps — PowerShell Monitoring and Troubleshooting Runbook

Version: 1.1
Last updated: 2026-08-28
Audience: application teams, DevOps engineers, cloud support, technical advisors

Purpose

This runbook provides reusable PowerShell and Azure CLI commands for monitoring and troubleshooting any Azure Container App (ACA). It is intentionally resource-agnostic and uses placeholders instead of project-specific names.

It covers:

  • subscription and resource discovery;
  • Container App, environment, revision, replica, image, identity and registry state;
  • Key Vault references without displaying secret values;
  • application and system logs;
  • ingress, health, scaling, metrics and Log Analytics;
  • RBAC and common deployment failures;
  • safe remediation, revision restart and rollback commands;
  • sample input and sanitized sample output.

Safety conventions

Commands marked READ-ONLY do not modify Azure resources. Commands marked CHANGES AZURE create a revision or update resource configuration.

Never:

  • print Key Vault secret values to console or pipeline logs;
  • place credentials directly in scripts, YAML, release definitions or command history;
  • use a personal account as a permanent pipeline identity;
  • assume provisioningState=Succeeded means the application process is healthy;
  • use mutable image tags such as latest as the only production deployment identifier.

Prerequisites

Install and verify:

az version
az extension show --name containerapp --output table
$PSVersionTable.PSVersion

Recommended minimum access for monitoring:

Scope Role or action Purpose
Subscription or resource group Reader Discover and inspect resources
Container App Container Apps Contributor Only when updates are required
User-assigned identity Managed Identity Operator Required when a deployment links an identity
ACR AcrPull for runtime; appropriate build role for pipeline Pull or build images
Key Vault Key Vault Secrets User for runtime Resolve secret values

Contributor does not grant Key Vault data-plane secret access and cannot create RBAC role assignments.

3. Capture a Container App snapshot

High-level snapshot — READ-ONLY

az containerapp show `
  --name $AppName `
  --resource-group $ResourceGroup `
  --query "{
    state:properties.provisioningState,
    environment:properties.environmentId,
    latestRevision:properties.latestRevisionName,
    activeRevisionsMode:properties.configuration.activeRevisionsMode,
    image:properties.template.containers[0].image,
    minReplicas:properties.template.scale.minReplicas,
    maxReplicas:properties.template.scale.maxReplicas,
    fqdn:properties.configuration.ingress.fqdn
  }" `
  --output jsonc

Sample output:

{
  "activeRevisionsMode": "Single",
  "fqdn": null,
  "image": "acrsample.azurecr.io/orders-worker:10452",
  "latestRevision": "orders-worker--0000008",
  "maxReplicas": 5,
  "minReplicas": 1,
  "state": "Succeeded"
}

Interpretation:

  • Succeeded means the ARM operation succeeded; inspect revision and replica health separately.
  • fqdn=null is normal for a background worker without ingress.
  • an immutable image tag such as a build ID is preferred over latest.

Query ARM directly when the Container Apps extension returns unexpected nulls — READ-ONLY

$AppId = az containerapp show `
  --name $AppName `
  --resource-group $ResourceGroup `
  --query id `
  --output tsv

az resource show `
  --ids $AppId `
  --api-version "2024-03-01" `
  --query "{identity:identity,configuration:properties.configuration,template:properties.template}" `
  --output jsonc

Use this when CLI extension serialization appears inconsistent with Portal or ARM.

Common identity split

Identity Recommended responsibility Typical roles
Pipeline identity Build and update ACA Container Apps Contributor; ACR build role; Managed Identity Operator on the runtime identity
Runtime identity Pull image and read runtime secrets AcrPull; Key Vault Secrets User
Personal account Temporary diagnostics/bootstrap Reader or time-bound Contributor through PIM

Avoid using the runtime identity as the pipeline deployment identity.

7. Key Vault references and environment variables

Inspect secret metadata safely — READ-ONLY

az containerapp show `
  --name $AppName `
  --resource-group $ResourceGroup `
  --query "properties.configuration.secrets[].{name:name,keyVaultUrl:keyVaultUrl,identity:identity}" `
  --output table

This displays references, not secret values.

Interpretation:

  • secrets=null: no ACA secrets are configured.
  • a Key Vault value existing does not automatically create an ACA secret reference.
  • the reference requires keyVaultUrl and an identity with secret get permission.

Inspect environment mappings safely — READ-ONLY

az containerapp show `
  --name $AppName `
  --resource-group $ResourceGroup `
  --query "properties.template.containers[].env[].{name:name,secretRef:secretRef,value:value}" `
  --output table

For sensitive settings, expect secretRef and no plaintext value.

Generic Key Vault reference update — CHANGES AZURE

Inputs:

$SecretName = "<aca-secret-name>"
$EnvironmentVariableName = "<ENVIRONMENT_VARIABLE_NAME>"
$IdentityId = az identity show `
  --name $IdentityName `
  --resource-group $ResourceGroup `
  --query id `
  --output tsv
$SecretUri = "https://$KeyVaultName.vault.azure.net/secrets/$SecretName"

Update:

az containerapp secret set `
  --name $AppName `
  --resource-group $ResourceGroup `
  --secrets "$SecretName=keyvaultref:$SecretUri,identityref:$IdentityId" `
  --output none

az containerapp update `
  --name $AppName `
  --resource-group $ResourceGroup `
  --set-env-vars "$EnvironmentVariableName=secretref:$SecretName" `
  --output none

The caller needs ACA write permission and userAssignedIdentities/assign/action on the linked identity. The runtime identity, not necessarily the caller, needs Key Vault secret read access.

8. Revisions and replicas

List revisions — READ-ONLY

az containerapp revision list `
  --name $AppName `
  --resource-group $ResourceGroup `
  --query "[].{name:name,active:properties.active,health:properties.healthState,replicas:properties.replicas,created:properties.createdTime,image:properties.template.containers[0].image}" `
  --output table

Sample output:

Name                       Active  Health    Replicas  Image
-------------------------  ------  --------  --------  ------------------------------------------
orders-worker--0000008     True    Healthy   1         acrsample.azurecr.io/orders-worker:10452
orders-worker--0000007     False   Healthy   0         acrsample.azurecr.io/orders-worker:10391

List replicas for a revision — READ-ONLY

$RevisionName = az containerapp show `
  --name $AppName `
  --resource-group $ResourceGroup `
  --query properties.latestRevisionName `
  --output tsv

az containerapp replica list `
  --name $AppName `
  --resource-group $ResourceGroup `
  --revision $RevisionName `
  --output table

Restart a revision — CHANGES AZURE

az containerapp revision restart `
  --name $AppName `
  --resource-group $ResourceGroup `
  --revision $RevisionName

Use restart after a Key Vault rotation when immediate secret refresh is required. Confirm impact for stateful or long-running workers.

Activate an older revision for rollback — CHANGES AZURE

$PreviousRevision = "<previous-revision-name>"

az containerapp revision activate `
  --name $AppName `
  --resource-group $ResourceGroup `
  --revision $PreviousRevision

For single-revision mode, prefer redeploying the previous immutable image tag through the pipeline so history remains auditable.

Recent application logs — READ-ONLY

az containerapp logs show `

  --type console `
  --tail 100

Follow application logs — READ-ONLY

az containerapp logs show `

  --resource-group $ResourceGroup `
  --type console `
  --follow `
  --tail 30

System logs — READ-ONLY

az containerapp logs show `
  --name $AppName `
  --resource-group $ResourceGroup `
  --type system `
  --tail 100

Use application logs for exceptions and startup output. Use system logs for image pull, scheduling, scaling, revision and platform events.

Do not pass --output text; current Container Apps log commands accept formats such as json, jsonc, table, tsv, yaml, yamlc or no explicit output option.

Corporate proxy certificate errors

Symptom:

SSLCertVerificationError: unable to get local issuer certificate

This can affect local Azure CLI log streaming while the ACA itself is healthy. Import the corporate root CA into the trusted bundle and configure REQUESTS_CA_BUNDLE according to company policy. Do not disable TLS verification globally.

10. Ingress and health endpoint

Inspect ingress — READ-ONLY

az containerapp show `
  --name $AppName `
  --resource-group $ResourceGroup `
  --query "properties.configuration.ingress" `
  --output jsonc

Check:

  • external: whether public ingress is enabled;
  • targetPort: must match the listening port inside the container;
  • transport: HTTP, HTTP/2 or TCP behavior;
  • traffic weights and revision labels.

Test a public health endpoint — READ-ONLY

$Fqdn = az containerapp show `
  --name $AppName `
  --resource-group $ResourceGroup `
  --query properties.configuration.ingress.fqdn `
  --output tsv

$HealthPath = "/health"
$Response = Invoke-WebRequest `
  -Uri "https://$Fqdn$HealthPath" `
  -Method Get `
  -TimeoutSec 15

$Response.StatusCode

Sample output:

200

Background workers normally have no ingress. Monitor their process, replica, queue lag and work completion instead.

11. Scale configuration

Inspect min/max replicas and rules — READ-ONLY

az containerapp show `
  --name $AppName `
  --resource-group $ResourceGroup `
  --query "properties.template.scale" `
  --output jsonc

Sample output:

{
  "minReplicas": 1,
  "maxReplicas": 5,
  "rules": [
    {
      "name": "queue-scale-rule"
    }
  ]
}

ScaledObjectCheckFailed: no triggers defined means a scale object exists without a usable trigger. For an always-on worker with no event scaler, use an intentional minReplicas configuration and remove invalid empty rules.

Update replica limits — CHANGES AZURE

az containerapp update `
  --name $AppName `
  --resource-group $ResourceGroup `
  --min-replicas 1 `
  --max-replicas 5

Evaluate cost, concurrency, downstream rate limits and duplicate processing before increasing replicas.

12. Azure Monitor metrics

Metric names vary by resource type and API evolution. Discover available metrics before querying them.

List available metric definitions — READ-ONLY

$AppId = az containerapp show `
  --name $AppName `
  --resource-group $ResourceGroup `
  --query id `
  --output tsv

az monitor metrics list-definitions `
  --resource $AppId `
  --query "[].{name:name.value,displayName:name.localizedValue,unit:unit,aggregation:primaryAggregationType}" `
  --output table

Query a discovered metric — READ-ONLY

$MetricName = "<metric-name-from-list-definitions>"
$StartTime = (Get-Date).ToUniversalTime().AddHours(-1).ToString("o")
$EndTime = (Get-Date).ToUniversalTime().ToString("o")

az monitor metrics list `
  --resource $AppId `
  --metric $MetricName `
  --start-time $StartTime `
  --end-time $EndTime `
  --interval PT5M `
  --aggregation Average,Maximum `
  --output jsonc

Monitor at least:

  • replica count and restart behavior;
  • CPU and memory utilization versus configured limits;
  • requests, latency and failure rate for HTTP applications;
  • event/queue backlog and processing age for workers;
  • revision health and deployment failure events.

13. Log Analytics queries

Resolve workspace ID — READ-ONLY

$WorkspaceResourceId = az containerapp env show `
  --name $EnvironmentName `
  --resource-group $ResourceGroup `
  --query properties.appLogsConfiguration.logAnalyticsConfiguration.customerId `
  --output tsv

Depending on configuration, this value may be a Log Analytics customer/workspace ID rather than an ARM resource ID.

Recent console errors — READ-ONLY

ContainerAppConsoleLogs_CL
| where TimeGenerated > ago(1h)
| where ContainerAppName_s == "<container-app-name>"
| where Log_s has_any ("ERROR", "Exception", "Traceback", "Fatal")
| project TimeGenerated, RevisionName_s, ContainerName_s, Log_s
| order by TimeGenerated desc

Recent system events — READ-ONLY

ContainerAppSystemLogs_CL
| where TimeGenerated > ago(1h)
| where ContainerAppName_s == "<container-app-name>"
| project TimeGenerated, RevisionName_s, Reason_s, Log_s
| order by TimeGenerated desc

Detect repeated container termination — READ-ONLY

ContainerAppSystemLogs_CL
| where TimeGenerated > ago(24h)
| where ContainerAppName_s == "<container-app-name>"
| where Reason_s in ("ContainerTerminated", "ContainerCrashing")
| summarize Terminations=count() by bin(TimeGenerated, 15m), RevisionName_s
| order by TimeGenerated desc

Table and column names can vary with diagnostic settings. Use the Logs schema browser to confirm the actual names in the workspace.

15. External dependency and endpoint validation

Use this pattern only when the current identity is authorized to read the secret. The value is held in memory and never printed.

$SecretName = "<api-key-secret-name>"
$Endpoint = "https://api.example.com/health-or-whoami"
$ApiKey = $null

try {
  $ApiKey = az keyvault secret show `
    --vault-name $KeyVaultName `
    --name $SecretName `
    --query value `
    --output tsv `
    --only-show-errors

  if ([string]::IsNullOrWhiteSpace($ApiKey)) {
    throw "Secret is empty."
  }

  $Headers = @{ Authorization = "Bearer $ApiKey" }
  $Response = Invoke-WebRequest `
    -Uri $Endpoint `
    -Headers $Headers `
    -Method Get `
    -TimeoutSec 30

  Write-Host "HTTP $($Response.StatusCode)"
}
finally {
  $ApiKey = $null
}

Interpretation:

  • 401 Invalid API Key: the endpoint received a key but rejected it.
  • 401 Wrong API endpoint: the key belongs to another region, tenant or endpoint.
  • 404 no Route matched: host is reachable but the requested API route does not exist there.
  • timeout/DNS/TLS failure: investigate egress, proxy, firewall, private DNS and CA trust.

For a vendor SDK, test the exact discovery or whoami route used by the deployed SDK, not only a generic /models or /health endpoint.

Mistral Workflows deployment and worker status

This subsection applies only when the Container App hosts a Mistral Workflows worker. It checks the Maia/Mistral control plane, not the Azure resource state.

Inputs:

Workflow API base : https://api.maia.dc.mistral.ai
Deployment name  : default
Authentication   : Mistral API key supplied interactively or through a secret environment variable

PowerShell — query deployment and workers — READ-ONLY

Prefer an interactive secure prompt. Do not use $ApiKey = "actual-secret" because the value can remain in PowerShell history, transcripts or screen recordings.

$WorkflowApiBase = "https://api.maia.dc.mistral.ai"
$DeploymentName  = "default"
$SecureApiKey    = Read-Host "Mistral API key" -AsSecureString
$ApiKey          = [Net.NetworkCredential]::new("", $SecureApiKey).Password

try {
  $Uri = "$WorkflowApiBase/v1/workflows/deployments/$DeploymentName"
  $Deployment = Invoke-RestMethod `
    -Method Get `
    -Uri $Uri `
    -Headers @{ Authorization = "Bearer $ApiKey" } `
    -TimeoutSec 30

  $Deployment |
    Select-Object name, is_active, worker_count, active_worker_count |
    Format-List

  $Deployment.workers |
    Select-Object name, is_active, created_at, updated_at |
    Format-Table -AutoSize

  if (-not $Deployment.is_active -or $Deployment.active_worker_count -lt 1) {
    throw "[FAILED] Deployment '$DeploymentName' has no active worker."
  }

  if ($Deployment.active_worker_count -lt $Deployment.worker_count) {
    Write-Warning "[WARNING] Only $($Deployment.active_worker_count)/$($Deployment.worker_count) workers are active."
  }
  else {
    Write-Host "[OK] All $($Deployment.active_worker_count) registered workers are active." -ForegroundColor Green
  }
}
catch {
  if ($_.Exception.Response) {
    $StatusCode = [int]$_.Exception.Response.StatusCode
    Write-Error "Workflow deployment API request failed. HTTP status: $StatusCode"
  }
  else {
    Write-Error $_.Exception.Message
  }
  throw
}
finally {
  $ApiKey = $null
  Remove-Variable ApiKey, SecureApiKey -ErrorAction SilentlyContinue
}

For automation, inject a secret environment variable from the CI/CD secret store and remove it immediately after use:

$ApiKey = $env:MISTRAL_API_KEY
if ([string]::IsNullOrWhiteSpace($ApiKey)) {
  throw "MISTRAL_API_KEY is not set."
}

# Run the same Invoke-RestMethod block here.

$ApiKey = $null
Remove-Item Env:MISTRAL_API_KEY -ErrorAction SilentlyContinue

Sanitized sample output:

name                : default
is_active           : True
worker_count        : 2
active_worker_count : 2

name                                      is_active created_at                 updated_at
----                                      --------- ----------                 ----------
orders-worker--0000012-6f8b7c9d4f-abc12   True      2026-08-28T07:28:10Z       2026-08-28T07:31:42Z
orders-worker--0000012-6f8b7c9d4f-def34   True      2026-08-28T07:28:11Z       2026-08-28T07:31:40Z

[OK] All 2 registered workers are active.

Sample degraded output — investigate the inactive worker:

name                : default
is_active           : True
worker_count        : 2
active_worker_count : 1

WARNING: [WARNING] Only 1/2 workers are active.

Sample failed output — no workflow execution capacity is available:

name                : default
is_active           : False
worker_count        : 1
active_worker_count : 0

Exception: [FAILED] Deployment 'default' has no active worker.

Sample authentication failure:

Invoke-RestMethod: Response status code does not indicate success: 401 (Unauthorized).
Workflow deployment API request failed. HTTP status: 401

Interpretation:

  • is_active=True and active_worker_count > 0: the deployment has at least one active worker.
  • worker_count > active_worker_count: one or more registered workers are stale, disconnected or starting.
  • worker_count > 0 and active_worker_count=0: Azure may report the ACA revision as healthy while no worker is available to execute workflows.
  • 404: verify the deployment name and API base URL.
  • 401 Invalid API Key: verify the secret value and rotation state.
  • 401 Wrong API endpoint: the key and Maia/Mistral API base belong to different environments or regions.

Bash — query deployment and workers — READ-ONLY

This example requires curl, jq and column. The silent prompt prevents the API key from being echoed.

#!/usr/bin/env bash
set -euo pipefail

WORKFLOW_API_BASE="https://api.maia.dc.mistral.ai"
DEPLOYMENT_NAME="default"

read -r -s -p "Mistral API key: " API_KEY
printf '\n'
trap 'unset API_KEY' EXIT

DEPLOYMENT_JSON="$({
  curl --fail-with-body --silent --show-error \
    --connect-timeout 10 \
    --max-time 30 \
    --header "Authorization: Bearer ${API_KEY}" \
    "${WORKFLOW_API_BASE}/v1/workflows/deployments/${DEPLOYMENT_NAME}"
})"

printf '%s' "$DEPLOYMENT_JSON" |
  jq '{name, is_active, worker_count, active_worker_count}'

printf '%s' "$DEPLOYMENT_JSON" |
  jq -r '
    ["NAME", "ACTIVE", "CREATED_AT", "UPDATED_AT"],
    (.workers[]? | [.name, (.is_active | tostring), .created_at, .updated_at])
    | @tsv
  ' | column -t -s $'\t'

worker_count="$(printf '%s' "$DEPLOYMENT_JSON" | jq -r '.worker_count // 0')"
active_worker_count="$(printf '%s' "$DEPLOYMENT_JSON" | jq -r '.active_worker_count // 0')"
deployment_active="$(printf '%s' "$DEPLOYMENT_JSON" | jq -r '.is_active // false')"

if [[ "$deployment_active" != "true" || "$active_worker_count" -lt 1 ]]; then
  printf '[FAILED] Deployment %s has no active worker.\n' "$DEPLOYMENT_NAME" >&2
  exit 2
elif [[ "$active_worker_count" -lt "$worker_count" ]]; then
  printf '[WARNING] Only %s/%s workers are active.\n' \
    "$active_worker_count" "$worker_count" >&2
else
  printf '[OK] All %s registered workers are active.\n' "$active_worker_count"
fi

unset DEPLOYMENT_JSON API_KEY
trap - EXIT

18. Monitoring cadence

After every deployment

  • Confirm the immutable image tag matches the pipeline build ID.
  • Confirm latest revision health and replica count.
  • Confirm identity, registry and required secret references are present.
  • Inspect startup application logs for exceptions.
  • Inspect system logs for image pull, scheduling and scale errors.
  • Run application health or worker dependency checks.
  • Preserve the previous image tag for rollback.

Daily operational checks

  • Failed or unhealthy revisions.
  • Container restarts and process exit codes.
  • CPU and memory saturation.
  • Replica count versus workload.
  • HTTP error rate/latency or queue backlog/processing age.
  • Key Vault, ACR and external dependency failures.
  • Recent policy or RBAC changes.

Incident checklist

  1. Record timestamp, subscription, resource group, app and latest revision.
  2. Capture the read-only snapshot.
  3. Check system health and Azure Activity Log.
  4. Compare current image/configuration with the last known good revision.
  5. Inspect application and system logs.
  6. Validate identity, registry and Key Vault reference chains.
  7. Validate external endpoints using the exact SDK route.
  8. Decide between forward fix, restart or rollback.
  9. Verify recovery with health, logs, metrics and business-level processing.
  10. Document root cause, remaining risk and preventive action.

19. Production recommendations

  • Use infrastructure as code to reconcile ACA identity, registry, secrets, environment variables, scale and ingress on both create and update paths.
  • Separate infrastructure provisioning from application image deployment, but validate their contract in the pipeline.
  • Use workload identity federation for Azure DevOps Service Connections.
  • Scope deployment roles to the target resource group or resource whenever possible.
  • Give runtime identities read-only secret access; avoid Key Vault Secrets Officer unless mutation is required.
  • Add deployment verification and automatic failure when revisions are unhealthy.
  • Store logs centrally and alert on termination, unhealthy revisions, sustained resource saturation and dependency failures.
  • Use immutable tags/digests and document rollback procedures.
  • Rotate any credential exposed in source code, release definitions, terminal history, screenshots or tickets.
