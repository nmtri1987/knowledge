Azure Container Apps troubleshooting reference

maia-wf-worker - PowerShell and Azure CLI runbook

Last reviewed: 2026-08-28 Scope: Azure Container Apps worker deployment, revisions, logs, managed identity, ACR, Key Vault references, Azure RBAC, federated credentials, and Mistral 401 Wrong API endpoint.

This runbook uses the actual resources from the troubleshooting session:

Subscription IDc0149d25-cc9a-4114-acad-15bc8a8c0546
Resource grouprg-weu-azu-aidlc-sb
Container Appmaia-wf-worker

Safety rule: Never print, paste, or log secret values. The commands below inspect secret names, references, status, timestamps, versions, identities, and RBAC only. Do not use --debug while handling secrets.

0. Session variables and preflight

Set the shared variables once at the start of the PowerShell session:

$subscription   = "subs-bis-sandbox"
$subscriptionId = "c0149d25-cc9a-4114-acad-15bc8a8c0546"
$rg             = "rg-weu-azu-aidlc-sb"
$app            = "maia-wf-worker"
$container      = "maia-wf-worker-container"
$identity       = "maia-wf-identity"
$kv             = "kv-maia-wf"
$acr            = "acrmaiawf"

Confirm the CLI and Container Apps extension are available:

az version
az extension show --name containerapp -o table

If the extension is missing, install it. If it is old, update it:

az extension add --name containerapp --upgrade

This changes only the local CLI installation. It does not create an ACA revision.

1. Wrong subscription or unregistered resource provider

Likely cause

Azure CLI is using subs-bis-cds-np instead of subs-bis-sandbox, or Microsoft.App is not registered in the selected subscription. The provider error occurs before Azure reaches maia-wf-worker.

How to check

az account show `
  --query "{Name:name, Id:id, TenantId:tenantId}" `
  -o table

az provider show `
  --namespace Microsoft.App `
  --query "registrationState" `
  -o tsv

Confirm the resource resolves in the selected subscription:

az resource show `
  --resource-group $rg `
  --name $app `
  --resource-type Microsoft.App/containerApps `
  --query id `
  -o tsv

Recommended fix

Switch to the known subscription:

az account set --subscription $subscription

az account show `
  --query "{Name:name, Id:id}" `
  -o table

If the correct subscription is selected and the provider is still unregistered:

az provider register `
  --namespace Microsoft.App `
  --wait

Verify that the final output is Registered:

az provider show `
  --namespace Microsoft.App `
  --query "registrationState" `
  -o tsv

Production notes

  • These commands do not create an ACA revision.
  • Provider registration requires subscription-scope permission. Resource-group Contributor alone may be insufficient.
  • Always verify the subscription before running any update, restart, RBAC, or secret operation.

2. Show Container App properties safely

Likely cause

The deployment may be incomplete: provisioningState=Failed, or identity, registry, secrets, and containers may be null.

How to check

Show the high-value properties without retrieving secret values:

az containerapp show `
  --name $app `
  --resource-group $rg `
  --query "{
    state:properties.provisioningState,
    deploymentErrors:properties.deploymentErrors,
    revisionMode:properties.configuration.activeRevisionsMode,
    latestRevision:properties.latestRevisionName,
    latestReadyRevision:properties.latestReadyRevisionName,
    identity:identity,
    registries:properties.configuration.registries,
    secrets:properties.configuration.secrets[].{
      name:name,
      keyVaultUrl:keyVaultUrl,
      identity:identity
    },
    containers:properties.template.containers[].{
      name:name,
      image:image,
      resources:resources,
      env:env
    }
  }" `
  -o jsonc

Compact state view:

az containerapp show `
  -n $app `
  -g $rg `
  --query "{
    state:properties.provisioningState,
    latest:properties.latestRevisionName,
    ready:properties.latestReadyRevisionName,
    fqdn:properties.configuration.ingress.fqdn
  }" `
  -o table

Recommended fix

  • If state=Failed and the template sections are null, inspect deployment and activity logs before recreating the app.
  • If the app is provisioned but a revision fails, continue with revision and log checks below.
  • Do not assume missing Key Vault secrets are the root cause unless system logs report secret resolution failure.

Production notes

These commands are read-only and do not create a revision.

3. List revisions and verify the active revision

Likely cause

An update created a new revision, but the old revision is still active; the newest revision is stuck in Activating; or traffic/runtime work is still handled by an older revision.

How to check

List all revisions, including inactive revisions:

az containerapp revision list `
  --name $app `
  --resource-group $rg `
  --all `
  --query "[].{
    Revision:name,
    Active:properties.active,
    Created:properties.createdTime,
    RunningState:properties.runningState,
    HealthState:properties.healthState,
    Replicas:properties.replicas
  }" `
  -o table

Check revision mode:

az containerapp show `
  -n $app `
  -g $rg `
  --query "properties.configuration.activeRevisionsMode" `
  -o tsv

Resolve the newest active revision safely:

$revision = az containerapp revision list `
  -n $app `
  -g $rg `
  --all `
  --query 'sort_by([?properties.active==`true`], &properties.createdTime)[-1].name' `
  -o tsv

Write-Host "Newest active revision: $revision"

Inspect it:

az containerapp revision show `
  -n $app `
  -g $rg `
  --revision $revision `
  --query "properties.{
    active:active,
    createdTime:createdTime,
    runningState:runningState,
    healthState:healthState,
    replicas:replicas,
    containers:template.containers[].{
      name:name,
      image:image,
      env:env
    }
  }" `
  -o jsonc

Cross-check the app's latest and latest-ready revision names:

az containerapp show `
  -n $app `
  -g $rg `
  --query "{
    latest:properties.latestRevisionName,
    latestReady:properties.latestReadyRevisionName
  }" `
  -o table

For an app with ingress, inspect traffic allocation:

az containerapp ingress traffic show `
  -n $app `
  -g $rg `
  -o table

Recommended fix

Restart an existing revision after a secret rotation or transient failure:

az containerapp revision restart `
  -n $app `
  -g $rg `
  --revision $revision

Restarting does not create a new revision.

If multiple-revision mode is intentional and the new revision is verified healthy, deactivate the old revision:

az containerapp revision deactivate `
  -n $app `
  -g $rg `
  --revision "maia-wf-worker--0000005"

Deactivation does not create a new revision.

For this background worker, use single revision mode unless concurrent revisions are deliberately required:

az containerapp revision set-mode `
  -n $app `
  -g $rg `
  --mode single

Changing revision mode is application-scoped and does not create a new revision.

Production notes

  • Do not deactivate the previous healthy revision while the new revision is Activating or HealthState=None.
  • Expected validation: latestRevisionName equals latestReadyRevisionName, and the target revision is active, Running, and Healthy.
  • Two active worker revisions can process work concurrently. Confirm the workflow supports multiple workers, idempotency, duplicate delivery, ordering, and safe retries before enabling this deliberately.

4. Check console and system logs

Likely cause

System logs explain image pulls, secret resolution, scheduling, and container lifecycle. Console logs explain application startup and errors such as 401 Wrong API endpoint.

How to check

Follow console logs for a specific revision:

az containerapp logs show `
  -n $app `
  -g $rg `
  --revision $revision `
  --container $container `
  --type console `
  --follow

Read recent console logs without following:

az containerapp logs show `
  -n $app `
  -g $rg `
  --revision $revision `
  --container $container `
  --type console `
  --tail 200

Read platform/system logs:

az containerapp logs show `
  -n $app `
  -g $rg `
  --type system `
  --tail 200

Useful system-log patterns:

Failed to pull image
Key Vault
ManagedIdentity
Forbidden
403
failed to resolve secret
ContainerTerminated
ProcessExited

Recommended fix

Use the log category to choose the next check:

EvidenceNext check
Image pull failureRegistry configuration and AcrPull
Key Vault/403/secret resolutionIdentity assignment, Key Vault reference, and RBAC
Container starts then exit code 1Application console log and configuration
Mistral 401 Wrong API endpointSERVER_URL and effective SDK config

Production notes

  • Log commands are read-only and do not create a revision.
  • Avoid printing full configuration objects if the application might log secret values. The observed Mistral configuration masked mistral_api_key, but do not assume every library does so.

5. Open /bin/sh and inspect the running container safely

Likely cause

The configured environment variable exists in ACA but the application ignores it, or the deployed package uses a different config key.

How to check

Open a shell on the selected revision:

az containerapp exec `
  -n $app `
  -g $rg `
  --revision $revision `
  --container $container `
  --command "/bin/sh"

If there is only one running revision/container, the shorter form is often enough:

az containerapp exec `
  -n maia-wf-worker `
  -g rg-weu-azu-aidlc-sb `
  --command "/bin/sh"

Inside the container, list environment variable names only:

printenv | cut -d= -f1 | sort

Check whether required variables are present without printing their values:

for name in MISTRAL_API_KEY AZURE_DEVOPS_ORG_URL AZURE_TENANT_ID AZURE_CLIENT_ID AZURE_CLIENT_SECRET SERVER_URL; do
  if printenv "$name" >/dev/null 2>&1; then
    echo "$name=SET"
  else
    echo "$name=MISSING"
  fi
done

Inspect how the installed Mistral Workflows package maps server_url:

grep -Rni "server_url" \
  /app/.venv/lib/python3.12/site-packages/mistralai/workflows/core/config

sed -n '1,220p' \
  /app/.venv/lib/python3.12/site-packages/mistralai/workflows/core/config/config.py

Recommended fix

If the image does not contain /bin/sh, use a shell that exists in the image. If the container crash-loops too quickly to exec, use console logs or temporarily deploy a diagnostic revision with an overridden startup command through the controlled deployment pipeline.

Production notes

  • exec is read-only unless commands run inside the container mutate data. It does not create a revision.
  • Do not run env, printenv without filtering, echo $SECRET, or token/API calls that expose credentials in terminal history or captured logs.
  • Changes made inside a container filesystem are ephemeral and must not be treated as a production fix.

6. Check environment variables and secret references

Likely cause

An environment variable is missing, points to the wrong ACA secret name, or exists but is not the variable read by the SDK.

How to check

Show environment mappings. Secret-backed variables display secretRef, not the secret value:

az containerapp show `
  -n $app `
  -g $rg `
  --query "properties.template.containers[].{
    container:name,
    env:env[].{
      name:name,
      value:value,
      secretRef:secretRef
    }
  }" `
  -o jsonc

Expected secret mappings include:

MISTRAL_API_KEY       -> secretRef: mistral-api-key
AZURE_DEVOPS_ORG_URL  -> secretRef: azure-devops-org-url
AZURE_TENANT_ID       -> secretRef: azure-tenant-id
AZURE_CLIENT_ID       -> secretRef: azure-client-id
AZURE_CLIENT_SECRET   -> secretRef: azure-client-secret

Show the environment of a specific revision:

az containerapp revision show `
  -n $app `
  -g $rg `
  --revision $revision `
  --query "properties.template.containers[0].env" `
  -o table

Recommended fix - update a normal environment variable

The Mistral worker reads SERVER_URL for worker.server_url. Update the correct variable:

az containerapp update `
  -n $app `
  -g $rg `
  --set-env-vars "SERVER_URL=https://api.mistral.ai"

This changes properties.template and creates a new revision.

Remove the unused or misleading variable:

az containerapp update `
  -n $app `
  -g $rg `
  --remove-env-vars MISTRAL_API_URL

This also creates a new revision.

Prefer one update, and therefore one new revision, when both changes are needed:

az containerapp update `
  -n $app `
  -g $rg `
  --remove-env-vars MISTRAL_API_URL `
  --set-env-vars "SERVER_URL=https://api.mistral.ai"

Recommended fix - map an ACA secret to an environment variable

az containerapp update `
  -n $app `
  -g $rg `
  --set-env-vars `
    "MISTRAL_API_KEY=secretref:mistral-api-key" `
    "AZURE_DEVOPS_ORG_URL=secretref:azure-devops-org-url" `
    "AZURE_TENANT_ID=secretref:azure-tenant-id" `
    "AZURE_CLIENT_ID=secretref:azure-client-id" `
    "AZURE_CLIENT_SECRET=secretref:azure-client-secret"

Changing environment mappings creates a new revision.

Production notes

  • Validate the new revision before retiring the previous revision.
  • Do not use mutable image tags such as latest; keep an immutable build tag such as 117418 or, preferably, an image digest.
  • If worker.server_url changes but agent.mistral_client_server_url remains on the EU endpoint, inspect the package configuration and set the separate supported client setting. Do not invent an environment variable name.

7. Check and update Key Vault secrets safely

Likely cause

One of the five secrets is missing, disabled, expired, or has an outdated version:

mistral-api-key
azure-devops-org-url
azure-tenant-id
azure-client-id
azure-client-secret

How to check

List secret names only:

az keyvault secret list `
  --vault-name $kv `
  --query "[].{
    Name:name,
    Enabled:attributes.enabled,
    Updated:attributes.updated,
    Expires:attributes.expires
  }" `
  -o table

Inspect metadata and version ID without returning a value:

$secretNames = @(
  "mistral-api-key",
  "azure-devops-org-url",
  "azure-tenant-id",
  "azure-client-id",
  "azure-client-secret"
)

foreach ($secretName in $secretNames) {
  az keyvault secret show `
    --vault-name $kv `
    --name $secretName `
    --query "{
      Name:name,
      Enabled:attributes.enabled,
      Updated:attributes.updated,
      Expires:attributes.expires,
      VersionId:id
    }" `
    -o jsonc
}

Recommended fix - update a Key Vault value interactively

Use a secure prompt and suppress command output. This avoids displaying the value, although the CLI still receives the value as a process argument on the local machine:

$secureValue = Read-Host "Enter new value for mistral-api-key" -AsSecureString
$plainValue = ConvertFrom-SecureString $secureValue -AsPlainText

try {
  az keyvault secret set `
    --vault-name $kv `
    --name "mistral-api-key" `
    --value $plainValue `
    --output none
}
finally {
  $plainValue = $null
  $secureValue = $null
}

For Azure DevOps, store the input as a masked secret variable and reference the macro only inside the pipeline task:

# MISTRAL_API_KEY must be an Azure DevOps secret variable.
az keyvault secret set `
  --vault-name "kv-maia-wf" `
  --name "mistral-api-key" `
  --value "$(MISTRAL_API_KEY)" `
  --output none
The $(MISTRAL_API_KEY) example is Azure DevOps macro syntax. Do not paste it into an ordinary interactive PowerShell session.

Updating a Key Vault secret does not itself create an ACA revision.

Production notes

  • Prefer Key Vault, managed identity, and versionless secret references for rotation.
  • Never place secret values in source control, Docker images, Helm values, release scripts, pipeline YAML, screenshots, tickets, or chat.
  • If a real secret appeared in a screenshot or inline release script, treat it as compromised and rotate it.
  • Versionless Key Vault references are refreshed automatically, but restart the active revision for deterministic rollout and verification.

8. Check and update ACA Key Vault secret references

Likely cause

The ACA secret does not reference Key Vault, points to the wrong URL, uses the wrong identity, or the container environment maps to a different secret name.

How to check

az containerapp show `
  -n $app `
  -g $rg `
  --query "properties.configuration.secrets[].{
    Name:name,
    KeyVaultUrl:keyVaultUrl,
    Identity:identity
  }" `
  -o table

Expected versionless references:

https://kv-maia-wf.vault.azure.net/secrets/mistral-api-key
https://kv-maia-wf.vault.azure.net/secrets/azure-devops-org-url
https://kv-maia-wf.vault.azure.net/secrets/azure-tenant-id
https://kv-maia-wf.vault.azure.net/secrets/azure-client-id
https://kv-maia-wf.vault.azure.net/secrets/azure-client-secret

Recommended fix

Resolve the managed identity resource ID:

$identityId = az identity show `
  -n $identity `
  -g $rg `
  --query id `
  -o tsv

Create or update the ACA Key Vault references without exposing values:

az containerapp secret set `
  -n $app `
  -g $rg `
  --secrets `
    "mistral-api-key=keyvaultref:https://kv-maia-wf.vault.azure.net/secrets/mistral-api-key,identityref:$identityId" `
    "azure-devops-org-url=keyvaultref:https://kv-maia-wf.vault.azure.net/secrets/azure-devops-org-url,identityref:$identityId" `
    "azure-tenant-id=keyvaultref:https://kv-maia-wf.vault.azure.net/secrets/azure-tenant-id,identityref:$identityId" `
    "azure-client-id=keyvaultref:https://kv-maia-wf.vault.azure.net/secrets/azure-client-id,identityref:$identityId" `
    "azure-client-secret=keyvaultref:https://kv-maia-wf.vault.azure.net/secrets/azure-client-secret,identityref:$identityId" `
  --output none

ACA secrets are application-scoped. Adding or changing them does not create a new revision. Restart the active revision or deploy a new revision so running containers deterministically receive the update:

az containerapp revision restart `
  -n $app `
  -g $rg `
  --revision $revision

Remove an unused ACA secret only after no active revision references it:

az containerapp secret remove `
  -n $app `
  -g $rg `
  --secret-names "obsolete-secret"

Removing an ACA secret does not create a revision, but can break existing revisions that still reference it.

Production notes

  • Key Vault Secrets User is sufficient for an ACA runtime identity that only reads secrets.
  • Key Vault Secrets Officer permits creating/updating/deleting secrets and is appropriate for a controlled deployment identity, not a least-privileged runtime identity.
  • Prefer separate deployment and runtime identities in production.

9. Check managed identity and Key Vault RBAC

Likely cause

maia-wf-identity is not assigned to the app or lacks Key Vault data-plane access.

How to check

Show the identity resource:

az identity show `
  -n $identity `
  -g $rg `
  --query "{
    Name:name,
    Id:id,
    ClientId:clientId,
    PrincipalId:principalId,
    Location:location
  }" `
  -o jsonc

Show the identities assigned to ACA:

az containerapp show `
  -n $app `
  -g $rg `
  --query identity `
  -o jsonc

Resolve IDs and list Key Vault role assignments:

$principalId = az identity show -n $identity -g $rg --query principalId -o tsv
$kvId = az keyvault show -n $kv -g $rg --query id -o tsv

az role assignment list `
  --assignee $principalId `
  --scope $kvId `
  --include-inherited `
  --query "[].{
    Role:roleDefinitionName,
    Scope:scope,
    PrincipalType:principalType
  }" `
  -o table

Recommended fix

If the identity is not assigned to ACA:

$identityId = az identity show -n $identity -g $rg --query id -o tsv

az containerapp identity assign `
  -n $app `
  -g $rg `
  --user-assigned $identityId

Identity assignment is application-scoped and does not normally create a new revision. Verify the app state afterward.

Grant the runtime identity read-only secret access at Key Vault scope, if authorized:

az role assignment create `
  --assignee-object-id $principalId `
  --assignee-principal-type ServicePrincipal `
  --role "Key Vault Secrets User" `
  --scope $kvId

RBAC changes do not create a revision. Allow for RBAC propagation, then restart and verify the active revision.

Production notes

  • Azure Resource Manager Contributor does not automatically grant Key Vault secret data-plane access.
  • Use least privilege and scope the role to kv-maia-wf, not the subscription.
  • If Key Vault uses private endpoints or firewall restrictions, also verify ACA network/DNS access; correct RBAC alone is insufficient.

10. Check registry configuration and AcrPull

Likely cause

The app uses the wrong registry identity, the image/tag does not exist, or maia-wf-identity lacks AcrPull on acrmaiawf.

How to check

Show registry and image configuration:

az containerapp show `
  -n $app `
  -g $rg `
  --query "{
    registries:properties.configuration.registries,
    containers:properties.template.containers[].{
      name:name,
      image:image
    }
  }" `
  -o jsonc

Confirm the repository and tag exist:

az acr repository show-tags `
  --name $acr `
  --repository "maia-wf-worker" `
  --query "[?@=='117418']" `
  -o table

Check AcrPull at ACR scope:

$principalId = az identity show -n $identity -g $rg --query principalId -o tsv
$acrId = az acr show -n $acr -g $rg --query id -o tsv

az role assignment list `
  --assignee $principalId `
  --scope $acrId `
  --include-inherited `
  --query "[].{
    Role:roleDefinitionName,
    Scope:scope
  }" `
  -o table

Recommended fix

Grant AcrPull if authorized:

az role assignment create `
  --assignee-object-id $principalId `
  --assignee-principal-type ServicePrincipal `
  --role AcrPull `
  --scope $acrId

If the registry identity setting is wrong:

$identityId = az identity show -n $identity -g $rg --query id -o tsv

az containerapp registry set `
  -n $app `
  -g $rg `
  --server "acrmaiawf.azurecr.io" `
  --identity $identityId

Registry configuration is application-scoped and does not create a new revision. Changing the container image with az containerapp update --image ... does create a new revision.

Production notes

  • Successful PulledImage proves the registry path and pull authorization worked for that attempt.
  • Use managed identity instead of registry username/password.
  • Pin immutable image tags or digests and keep rollback images available.

11. Check federated credentials and related identity details

Likely cause

Azure DevOps Workload Identity Federation may be mapped to the wrong user-assigned identity, issuer, subject, or audience.

This is relevant to the Azure DevOps service connection. It is not the cause of the observed Mistral whoami_async() 401 Wrong API endpoint after the container had already started.

How to check

List federated credentials on maia-wf-identity:

az identity federated-credential list `
  --identity-name $identity `
  --resource-group $rg `
  --query "[].{
    Name:name,
    Issuer:issuer,
    Subject:subject,
    Audiences:audiences
  }" `
  -o jsonc

Show a known credential:

az identity federated-credential show `
  --identity-name $identity `
  --resource-group $rg `
  --name "<federated-credential-name>" `
  -o jsonc

Validate these fields against the Azure DevOps service connection:

Issuer    = issuer shown by Azure DevOps
Subject   = subject identifier shown by Azure DevOps
Audience  = api://AzureADTokenExchange

The previously observed service connection subject ended with service connection ID:

5a5eb695-c0a3-4fd1-97a3-79847ac85572

Recommended fix

Create or change federated credentials only from the exact issuer/subject values supplied by the Azure DevOps service connection. Do not guess them. After creation, use Verify and save in Azure DevOps.

Production notes

  • Workload Identity Federation avoids long-lived client secrets for pipeline authentication.
  • Service connection authentication and Azure DevOps repository ACLs are separate. The service principal still needs explicit project/repository permissions.

12. Troubleshoot 401 Wrong API endpoint

Likely cause

The logs showed:

mistralai.workflows.worker_client.errors.sdkdefaulterror.SDKDefaultError:
API error occurred: Status 401. Body: {"detail":"Wrong API endpoint"}

The container had already pulled its image and started Python. Effective configuration showed:

worker.server_url = https://api.eu.mistral.ai
agent.mistral_client_server_url = https://api.eu.mistral.ai

ACA contained both:

SERVER_URL      = https://api.eu.mistral.ai
MISTRAL_API_URL = https://api.mistral.ai

The worker reads SERVER_URL for worker.server_url; setting only MISTRAL_API_URL did not override that field.

How to check

  1. Confirm that image pull and container startup succeeded in system logs.
  2. Confirm the exact failing call is Mistral worker_client.whoami_async().
  3. Show SERVER_URL and MISTRAL_API_URL in the revision environment; do not show API keys.
  4. Inspect the startup Configuration loaded log for both worker.server_url and agent.mistral_client_server_url.
  5. If necessary, inspect the installed package source using the /bin/sh commands in section 5.
az containerapp revision show `
  -n $app `
  -g $rg `
  --revision $revision `
  --query "properties.template.containers[0].env[?name=='SERVER_URL' || name=='MISTRAL_API_URL']" `
  -o table

Recommended fix

Update the setting the worker actually consumes and remove the misleading variable in a single revision:

az containerapp update `
  -n $app `
  -g $rg `
  --remove-env-vars MISTRAL_API_URL `
  --set-env-vars "SERVER_URL=https://api.mistral.ai"

This creates a new revision. Capture its name and follow only that revision's logs:

$newRevision = az containerapp show `
  -n $app `
  -g $rg `
  --query "properties.latestRevisionName" `
  -o tsv

az containerapp logs show `
  -n $app `
  -g $rg `
  --revision $newRevision `
  --container $container `
  --type console `
  --follow

Verification criteria

The fix is verified only when all are true:

New revision is Active
RunningState = Running
HealthState = Healthy
latestRevisionName = latestReadyRevisionName
worker.server_url = https://api.mistral.ai
No new "401 Wrong API endpoint"
Worker completes whoami/config discovery and remains running

If agent.mistral_client_server_url still shows https://api.eu.mistral.ai, inspect the installed version's supported config mapping and update that separate setting before model activities are used.

Production notes and remaining risks

  • This 401 is different from Entra ID/Azure DevOps authentication failures. The stack trace failed inside Mistral Workflows before Azure DevOps operations.
  • Do not rotate Azure client credentials merely because this particular error says 401; first identify the hostname, client, and response body.
  • Alert on repeated container exits, restart count, revision health, 401/403 rate, Mistral request latency, and worker heartbeat/config-discovery failures.
  • Use bounded retries with jitter. Authentication/configuration errors should not trigger aggressive retries or a retry storm.

13. One-pass read-only diagnostic script

This script performs read-only checks and does not print secret values:

$subscription = "subs-bis-sandbox"
$rg           = "rg-weu-azu-aidlc-sb"

Write-Host "=== SUBSCRIPTION ==="

Write-Host "`n=== ACA STATE ==="
az containerapp show -n $app -g $rg `
  --query "{
    State:properties.provisioningState,
    Mode:properties.configuration.activeRevisionsMode,
    Latest:properties.latestRevisionName,
    LatestReady:properties.latestReadyRevisionName
  }" -o table

Write-Host "`n=== REGISTRY AND IMAGE ==="
az containerapp show -n $app -g $rg `
  --query "{
    Registries:properties.configuration.registries,
    Containers:properties.template.containers[].{Name:name,Image:image}
  }" -o jsonc

Write-Host "`n=== KEY VAULT REFERENCES ==="
az containerapp show -n $app -g $rg `
  --query "properties.configuration.secrets[].{
    Name:name,
    KeyVaultUrl:keyVaultUrl,
    Identity:identity
  }" -o table

az containerapp show -n $app -g $rg `
  --query "properties.template.containers[].{
    Container:name,
    Env:env[].{Name:name,Value:value,SecretRef:secretRef}
  }" -o jsonc

Write-Host "`n=== REVISIONS ==="
az containerapp revision list -n $app -g $rg --all `
  --query "[].{
    Revision:name,
    Active:properties.active,
    Running:properties.runningState,
    Health:properties.healthState,
    Created:properties.createdTime
  }" -o table

Write-Host "`n=== KEY VAULT SECRET METADATA ==="

  "azure-tenant-id",
  "azure-client-id",
  "azure-client-secret"
)
foreach ($secretName in $secretNames) {
  az keyvault secret show -n $secretName --vault-name $kv `
    --query "{Name:name,Enabled:attributes.enabled,Updated:attributes.updated,Expires:attributes.expires}" `
    -o table
}

Write-Host "`n=== RECENT SYSTEM LOGS ==="
az containerapp logs show -n $app -g $rg --type system --tail 100

15. Final production checklist

  • Correct subscription and tenant verified before every write operation.
  • Microsoft.App is registered.
  • ACA provisioning state is Succeeded.
  • latestRevisionName equals latestReadyRevisionName after deployment.
  • Only intended revisions are active; traffic/runtime work is not accidentally split.
  • New revision is Running and Healthy before the previous revision is retired.
  • maia-wf-identity is assigned to ACA.
  • Runtime identity has Key Vault Secrets User at kv-maia-wf scope.
  • Runtime identity has AcrPull at acrmaiawf scope.
  • ACA uses Key Vault references; secret values are not stored in deployment files.
  • Secret environment mappings use secretRef.
  • Versionless Key Vault references and a controlled rotation/restart procedure are documented.
  • Immutable image tags/digests and rollback steps are available.
  • SERVER_URL=https://api.mistral.ai is visible in effective worker config.
  • No recurring 401 Wrong API endpoint, 403, secret resolution, image pull, or crash-loop errors.
  • Logs, metrics, traces, revision health, restart count, worker lag/heartbeat, and authentication failures are alerted.
  • Multiple workers are enabled only with tested idempotency, duplicate handling, retry control, and ordering assumptions.
