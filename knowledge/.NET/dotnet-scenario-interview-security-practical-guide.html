1. API đột nhiên mất 5–10 giây để phản hồi

Mục tiêu: xác định chính xác thời gian bị mất ở layer nào.

Nguyên nhân thường gặp

  • SQL query chậm / execution plan thay đổi.
  • External API timeout/retry.
  • Thread pool starvation do sync-over-async.
  • Redis/cache miss hàng loạt.
  • CPU/GC cao, memory pressure.
  • DNS/TLS/network latency.

Cách kiểm tra

  1. Application Insights → Transaction Search / Performance.
  2. Breakdown Server vs SQL vs HTTP dependency.
  3. SQL Query Store / Actual Execution Plan.
  4. dotnet-counters cho CPU, GC, ThreadPool.
  5. Kiểm tra deploy/change ngay trước thời điểm latency tăng.
Ví dụ thực tế ASP.NET Core
public async Task<OrderDto> GetOrderAsync(int id, CancellationToken ct)
{
    // Không dùng .Result / .Wait()
    var order = await _db.Orders
        .AsNoTracking()
        .SingleAsync(x => x.Id == id, ct);

    return _mapper.Map<OrderDto>(order);
}

Nếu query chiếm 7.8s trên tổng 8.1s thì không nên scale API trước; cần tối ưu query/index hoặc dữ liệu trước.

Thứ tự xử lý: APM → dependency breakdown → SQL/network/thread → sửa đúng bottleneck → đo lại p95/p99.
Production: đặt timeout cho outbound call; propagate CancellationToken; tránh retry mọi lỗi; dashboard p95/p99 theo endpoint, không chỉ average.
Security lens: liên quan trực tiếp Missing Rate Limiting. Scale-out không thay thế throttling; cần bảo vệ DB/downstream khỏi abusive traffic.

2. ASP.NET Core nhận 10.000 requests/phút và bắt đầu fail

10.000 RPM ≈ 167 RPS. Con số này không quá lớn với một API stateless tốt, nhưng có thể làm DB hoặc dependency nghẽn.

Kiểm tra trước

  • CPU, RAM, ThreadPool, socket, connection pool.
  • RPS theo instance và p95 latency.
  • DB CPU/IO/locks/connections.
  • Tỷ lệ cache hit.

Giải pháp

  • Scale out nhiều instance sau Load Balancer.
  • Stateless API; session chuyển Redis/DB nếu cần.
  • Cache read-heavy data.
  • Rate limiting / backpressure.
  • Queue tác vụ không cần xử lý đồng bộ.

builder.Services.AddRateLimiter(options =>

Production: với AKS/ACA hãy set resource requests/limits hợp lý, readiness probe, HPA/KEDA và giới hạn DB connection pool theo số replica để tránh scale API làm DB chết nhanh hơn.

3. Hai user cập nhật cùng record, người sau ghi đè người trước

Đây là bài toán optimistic concurrency.

Cách làm

  1. Thêm rowversion / concurrency token.
  2. Client gửi version cũ khi update.
  3. DB update với điều kiện ID + version.
  4. Không match → trả HTTP 409 Conflict.
  5. User reload/merge rồi retry.

Khi dùng pessimistic lock?

Khi conflict gây hậu quả lớn và thao tác rất ngắn, ví dụ giữ tồn kho cực ngắn. Không nên giữ DB lock qua thời gian user nhập liệu.

public class Product
{
    public int Id { get; set; }
    public decimal Price { get; set; }

    [Timestamp]
    public byte[] RowVersion { get; set; } = default!;
}
Production: 409 nên trả currentVersion/currentData để UI có thể hiển thị “record đã thay đổi” thay vì trả generic 500.
Security lens: kiểm tra Improper Certificate Validation, Sensitive Data in Logs và không đưa token vào URL.

4. External payment API intermittent failure

Nguyên nhân

  • Timeout phía provider.
  • Network/TLS/DNS chập chờn.
  • Rate limit 429.
  • Provider 5xx.
  • Client retry gây duplicate charge.

Cách xử lý

  • Timeout hợp lý.
  • Retry exponential backoff + jitter.
  • Circuit breaker.
  • Idempotency key.
  • Queue cho flow có thể async.
// Ví dụ ý tưởng với resilience pipeline
// Retry chỉ transient faults: 408, 429, 5xx.
// KHÔNG retry 400/401/403 một cách mù quáng.
Idempotency: Payment request có Idempotency-Key = orderId/paymentAttemptId. Provider hoặc API của ta lưu trạng thái key này để retry không tạo giao dịch thứ hai.
Production: retry budget phải nhỏ; tổng timeout của chuỗi service phải nằm trong SLA của request. Nếu upstream timeout 5s thì không thể để 3 retry × 5s.

5. Database là bottleneck: điều tra gì đầu tiên?

Checklist SQL

  • Top query theo CPU / duration / logical reads.
  • Execution plan: scan, key lookup, bad estimate.
  • Missing/unused index.
  • Blocking, lock waits.
  • SQL CPU, memory, IO latency.
  • Connection pool exhaustion.

Checklist EF Core

  • N+1 query.
  • AsNoTracking() cho read-only.
  • Projection Select() thay vì load full entity.
  • Không Include() cả graph quá lớn.
  • Batching / pagination.
var orders = await db.Orders
    .AsNoTracking()
    .Where(x => x.Status == OrderStatus.Pending)
    .Select(x => new OrderListItem(x.Id, x.Customer.Name, x.Total))
    .Take(100)
    .ToListAsync(ct);
Production: Query Store rất quan trọng để phát hiện regression sau deploy hoặc plan change. Index phải dựa trên workload thật, không phải “thấy query chậm thì add index”.

6. Background job đôi lúc chạy duplicate

Trong distributed system, “exactly once” rất khó. Thiết kế thực tế thường là at-least-once delivery + idempotent processing.

Defense layers

  1. Unique job/business key trong DB.
  2. Idempotent handler.
  3. Distributed lock khi thật sự cần.
  4. Retry có kiểm soát.
  5. Audit execution.

Distributed lock

  • On-prem: SQL hoặc Redis.
  • Azure: Redis, Blob Lease.
  • K8s: không dùng in-memory lock giữa nhiều pod.
CREATE UNIQUE INDEX UX_Payment_OrderId
ON PaymentProcessing(OrderId);
Production: lock chỉ là một lớp; unique constraint/idempotency trong DB mới là “last line of defense” khi worker crash sau khi đã xử lý nhưng trước khi ACK message.

7. ASP.NET Core memory tăng liên tục / nghi memory leak

Nguyên nhân .NET phổ biến

  • Static cache không giới hạn.
  • Event handler không unsubscribe.
  • Singleton giữ object graph lớn.
  • Timer/background service giữ reference.
  • Stream/IDisposable không dispose.
  • LOH pressure do object lớn.

Tool

  • dotnet-counters
  • dotnet-gcdump
  • dotnet-dump
  • Visual Studio Profiler
  • Application Insights / Prometheus + Grafana
Observe heap trend → Force/observe GC behavior → Capture dump → Compare object counts → Find retention path → Fix → Soak test
Production: memory cao chưa chắc là leak. .NET giữ heap để reuse. Cần nhìn “memory after GC” và object retention theo thời gian, không chỉ nhìn working set.

8. User thấy stale data: thiết kế cache thế nào?

Cache-aside

  1. Check cache.
  2. Miss → đọc DB.
  3. Set cache.
  4. Return.
  5. Write DB → invalidate cache.

TTL

  • Absolute expiration: hết hạn sau N phút.
  • Sliding expiration: gia hạn khi accessed.
  • Jitter TTL để tránh cache stampede.

Production: tránh cache dữ liệu security/permission quá lâu; với config/reference data có thể cache 5–30 phút tùy SLA freshness. Theo dõi hit ratio và cache evictions.
Security lens: file upload phải xét thêm XSS via File Upload, Path Traversal, Zip Slip, Arbitrary File Write và SSRF via File Upload.

9. Upload và xử lý file lớn 1GB+

Không nên đưa toàn bộ file qua RAM của API hoặc giữ HTTP connection trong suốt thời gian xử lý.

Thiết kế khuyến nghị Azure

  1. Client xin SAS upload URL.
  2. Client upload trực tiếp Blob Storage theo block/chunk.
  3. API ghi metadata + status.
  4. Event/Grid/Service Bus trigger Worker.
  5. Worker stream file, xử lý chunk.
  6. Update status để client poll / SignalR.

Lợi ích

  • API không giữ 1GB RAM.
  • Resume upload.
  • Scale worker độc lập.
  • Retry processing không cần upload lại.
Production: checksum, MIME validation, antivirus nếu cần, upload session ID, size limit, lifecycle policy cho blob tạm, dead-letter cho job lỗi.

10. SQL deadlock

Cách điều tra

  1. Capture deadlock graph bằng Extended Events.
  2. Xác định 2 transaction và resource đang giữ/chờ.
  3. Kiểm tra access order table/index.
  4. Giảm transaction duration.
  5. Thêm/sửa index nếu scan giữ lock quá nhiều.

Cách phòng

  • Luôn access resource cùng thứ tự.
  • Transaction càng ngắn càng tốt.
  • Không gọi external API trong transaction.
  • Cân nhắc READ_COMMITTED_SNAPSHOT.
Deadlock khác blocking: blocking có thể chờ rồi chạy tiếp; deadlock là cycle nên SQL Server chọn một transaction làm victim.
Production: có thể retry deadlock victim (error 1205), nhưng retry chỉ là safety net; vẫn phải sửa root cause.

11. Session state làm server memory tăng

Vấn đề

  • InProc session nằm trong memory từng instance.
  • Scale out dễ mất/không đồng nhất session.
  • Object lớn làm memory pressure.

Khuyến nghị

  • Ưu tiên stateless API.
  • Chỉ lưu session data tối thiểu.
  • Nếu bắt buộc: Redis distributed session.
  • Set timeout và cleanup.
Với API/microservice mới: nên tránh server-side session nếu có thể. Dùng JWT/claims + DB/Redis cho state cần chia sẻ.
Security lens: SOAP/XML cần kiểm tra XXE, XML Injection, XPath Injection và giới hạn parser để tránh XML bomb.

12. Tích hợp legacy SOAP service chậm và không ổn định

Resilience

  • Connect/read timeout.
  • Retry exponential backoff.
  • Circuit breaker.
  • Fallback/cache nếu business cho phép.
  • Queue nếu flow không cần sync.

Anti-corruption layer

Bọc SOAP bằng một adapter/service nội bộ. Domain code không phụ thuộc trực tiếp WSDL/generated types.

Retry vs Circuit Breaker: Retry xử lý lỗi ngắn hạn. Circuit breaker dừng gọi tạm thời khi dependency đang fail nhiều, giúp tránh “đánh tiếp vào service đang chết”.
Production: theo dõi latency/error riêng của legacy dependency và đặt timeout thấp hơn timeout của caller.

13. Gửi email cho hàng triệu user

Architecture

  1. API chỉ enqueue email request.
  2. Queue/Service Bus buffer workload.
  3. Worker scale theo backlog.
  4. Email provider: SendGrid/SES/SMTP relay.
  5. Webhook cập nhật delivered/bounced/complaint.

Cần quản lý

  • Rate limit provider.
  • Retry transient error.
  • Dead-letter queue.
  • Unsubscribe/bounce suppression.
  • Template/version.
  • Audit status.
Production: không retry vô hạn địa chỉ hard-bounce; phân biệt transient vs permanent failure. Với Service Bus nên lưu business key để handler idempotent.

14. API gọi nhiều service và phản hồi chậm

Ví dụ A=500ms, B=600ms, C=700ms. Gọi tuần tự ≈ 1.8s; gọi song song ≈ 700ms + overhead.

var aTask = serviceA.GetAsync(ct);
var bTask = serviceB.GetAsync(ct);
var cTask = serviceC.GetAsync(ct);

await Task.WhenAll(aTask, bTask, cTask);

return new AggregateDto(
    await aTask, await bTask, await cTask);
Không phải lúc nào cũng parallel. Nếu B phụ thuộc output của A thì bắt buộc tuần tự. Parallel quá nhiều có thể làm downstream quá tải.

Tối ưu thêm

  • Cache dữ liệu read-heavy.
  • Chỉ lấy field cần thiết.
  • Batch API.
  • Reduce chatty calls.

Resilience

  • Timeout từng dependency.
  • Fallback / graceful degradation.
  • Bulkhead/concurrency limit.
Production: nếu endpoint fan-out tới 10 service, xác suất có ít nhất một service lỗi tăng mạnh. Thiết kế partial response hoặc degrade feature nếu business cho phép.
Security lens: microservices làm auth/API surface tăng. Ưu tiên policy-based authorization, JWT validation, secret management, CORS và data minimization.

  • Strangler Fig.

A. Injection Attacks

SQL Injection

Critical · CWE-89

Khi nào bị?

Query SQL được ghép chuỗi trực tiếp từ input: search, sort, filter, login, report parameter.

Ví dụ thực tế

API tìm order nhận `customerName`; code ghép `WHERE CustomerName = '...'`. Input trở thành một phần cú pháp SQL thay vì chỉ là dữ liệu.

Mức độ nguy hiểm

Rò rỉ/sửa/xóa dữ liệu; bypass authentication; có thể ảnh hưởng toàn DB tùy quyền của account ứng dụng.

Cách kiểm tra

Search source cho `FromSqlRaw`, `ExecuteSqlRaw`, string interpolation/concatenation gần SQL; xem SQL Query/DB audit bất thường.

Code minh họa: vì sao lỗi và hướng sửa
// ❌ Vulnerable
var sql = $"SELECT * FROM Orders WHERE CustomerName = '{name}'";
var rows = db.Database.SqlQueryRaw<Order>(sql);

// ✅ Safer
var rows = await db.Orders
    .Where(x => x.CustomerName == name)
    .ToListAsync(ct);
Phòng tránh / production: Dùng LINQ/EF parameterization hoặc SQL parameters; tài khoản DB least privilege; không cho input điều khiển tên table/column nếu chưa allow-list.

Command Injection

Critical · CWE-78

Khi nào bị?

Ứng dụng gọi shell/OS command và ghép input user vào command line.

Ví dụ thực tế

Endpoint diagnostics cho phép user nhập hostname rồi chạy `cmd /c ping {host}`. Nếu shell parse thêm control characters thì input có thể biến thành command khác.

Mức độ nguy hiểm

Remote command execution với quyền của process/container; đọc secret, sửa file, lateral movement.

Cách kiểm tra

Tìm `Process.Start`, `cmd.exe`, `powershell`, `/bin/sh`, `bash -c`; quan sát child-process bất thường từ app.

Code minh họa: vì sao lỗi và hướng sửa
// ❌ Vulnerable
Process.Start("cmd.exe", $"/c ping {host}");

// ✅ Better: tránh shell và allow-list input
if (!Regex.IsMatch(host, @"^[a-zA-Z0-9.-]+$"))
    return BadRequest();
Process.Start(new ProcessStartInfo("ping", host) { UseShellExecute = false });
Phòng tránh / production: Tránh shell; dùng API/library tương ứng; allow-list input; chạy container/user không đặc quyền; egress/network policy.

LDAP Injection

High · CWE-90

Khi nào bị?

LDAP filter được ghép từ username/search text mà không escape ký tự LDAP đặc biệt.

Ví dụ thực tế

Ứng dụng tra user AD bằng filter kiểu `(&(objectClass=user)(uid={username}))`; input làm thay đổi cấu trúc filter.

Mức độ nguy hiểm

Bypass filter, đọc user/group không mong muốn, có thể làm sai logic authorization.

Cách kiểm tra

Search code tạo `DirectorySearcher.Filter`; log các filter lỗi/return count bất thường.

Code minh họa: vì sao lỗi và hướng sửa
// ❌
var filter = $"(&(objectClass=user)(uid={username}))";

// ✅
var safe = EscapeLdapFilter(username);
var filter = $"(&(objectClass=user)(uid={safe}))";
Phòng tránh / production: Escape theo LDAP filter rules; allow-list format username; không dùng query LDAP cho authorization nếu có thể lấy claims/groups tin cậy.

Log Injection (Log Forging)

Medium · CWE-117

Khi nào bị?

Đưa input trực tiếp vào log text, đặc biệt có CR/LF, khiến attacker tạo dòng log giả hoặc phá parser.

Ví dụ thực tế

API log `Login failed for {username}` nhưng username có newline → SIEM nhìn như có thêm một event hợp lệ.

Mức độ nguy hiểm

Làm sai audit trail, che dấu hành vi, gây alert giả; nguy hiểm cao hơn trong security/audit logs.

Cách kiểm tra

Tìm string concatenation trong logging; kiểm tra log chứa newline/control chars từ request fields.

Code minh họa: vì sao lỗi và hướng sửa
// ❌
logger.LogInformation("User input: " + input);

// ✅ structured logging
logger.LogInformation("User input: {Input}", SanitizeForLog(input));
Phòng tránh / production: Structured logging; encode/strip CRLF khi log raw input; giới hạn độ dài; không log nguyên request body.

XPath Injection

High · CWE-643

Khi nào bị?

XPath expression được nối chuỗi từ input thay vì parameter/biến an toàn.

Ví dụ thực tế

XML user store dùng `SelectSingleNode("//user[name='" + name + "']")`; input thay đổi predicate.

Mức độ nguy hiểm

Bypass login/filter, đọc node nhạy cảm trong XML.

Cách kiểm tra

Tìm `SelectSingleNode/SelectNodes` với interpolation/concatenation.

Code minh họa: vì sao lỗi và hướng sửa
// ❌
var node = doc.SelectSingleNode($"//user[name='{name}']");

// ✅
var nodes = doc.SelectNodes("//user")!
    .Cast<XmlNode>()
    .Where(x => x["name"]?.InnerText == name);
Phòng tránh / production: Không xây XPath từ input; dùng parser + compare value; nếu library hỗ trợ XPath variables thì bind variables.

XML Injection

High · CWE-91

Khi nào bị?

Tạo XML bằng string concatenation từ input.

Ví dụ thực tế

Ví dụ thực tế

Vue app có `VITE_API_SECRET` gọi trực tiếp partner API.

Mức độ nguy hiểm

Bất kỳ user nào mở DevTools đều lấy key; không thể coi front-end secret là secret.

Cách kiểm tra

Scan JS bundles/source maps; secret scanning.

Code minh họa: vì sao lỗi và hướng sửa
// ✅ browser -> your backend -> partner; backend gets secret from Key Vault
Phòng tránh / production: Không đặt server secret ở client; BFF/backend proxy; Managed Identity/OAuth delegated flows.

F. XML & Serialization

XXE (XML External Entity)

Critical · CWE-611

Khi nào bị?

XML parser cho phép DTD/external entity với XML untrusted.

Ví dụ thực tế

SOAP/upload XML có DOCTYPE; parser resolve local/network resources.

Mức độ nguy hiểm

Đọc local file, SSRF, DoS; tùy parser/config.

Cách kiểm tra

Search `XmlResolver`, `DtdProcessing.Parse`; test parser config.

Code minh họa: vì sao lỗi và hướng sửa
var settings = new XmlReaderSettings { DtdProcessing = DtdProcessing.Prohibit, XmlResolver = null };
Phòng tránh / production: Disable DTD/external entities; schema/size limits; network egress controls.

Insecure Deserialization (BinaryFormatter)

Critical · CWE-502

Khi nào bị?

Deserialize BinaryFormatter/unsafe formatter từ dữ liệu user.

Ví dụ thực tế

API nhận base64 blob và `BinaryFormatter.Deserialize`.

Mức độ nguy hiểm

Gadget chain có thể dẫn tới RCE; .NET đã deprecate/disable BinaryFormatter trong modern versions.

Cách kiểm tra

Search `BinaryFormatter`, `LosFormatter`, unsafe serializers.

Code minh họa: vì sao lỗi và hướng sửa
// ✅ use typed JSON/Protobuf with explicit contracts; never BinaryFormatter for untrusted data
Phòng tránh / production: Loại bỏ BinaryFormatter; typed serializer; integrity/authenticate data.

JSON Deserialization Attacks

Critical · CWE-502

Khi nào bị?

JSON.NET bật type metadata cho untrusted JSON (`TypeNameHandling` nguy hiểm).

Ví dụ thực tế

Deserializer cho client chỉ định `$type` và instantiate type ngoài dự kiến.

Mức độ nguy hiểm

Có thể instantiate gadget/type nguy hiểm → RCE/side effects.

Cách kiểm tra

Search `TypeNameHandling.Auto/All/Objects`; custom binder.

Code minh họa: vì sao lỗi và hướng sửa
var settings = new JsonSerializerSettings { TypeNameHandling = TypeNameHandling.None };
Phòng tránh / production: Không cho client chọn CLR type; typed DTO; nếu polymorphic thì discriminator allow-list.

XML Bomb (Billion Laughs)

High · CWE-776

Khi nào bị?

Parser expand entity đệ quy hoặc không giới hạn document/entity size.

Ví dụ thực tế

XML nhỏ expand thành lượng text cực lớn làm cạn RAM/CPU.

Mức độ nguy hiểm

DoS memory/CPU.

Cách kiểm tra

Monitor request size, memory spike; parser settings.

Code minh họa: vì sao lỗi và hướng sửa
var settings = new XmlReaderSettings { DtdProcessing = DtdProcessing.Prohibit, MaxCharactersInDocument = 5_000_000 };
Phòng tránh / production: Prohibit DTD; size/depth/time limits; request body limits.

Insecure YAML Deserialization

Critical · CWE-502

Khi nào bị?

YAML deserializer tạo arbitrary runtime types từ untrusted YAML.

Ví dụ thực tế

Upload config YAML được deserialize với unrestricted tags/type resolution.

Mức độ nguy hiểm

Gadget/side-effect execution hoặc logic manipulation tùy library.

Cách kiểm tra

Review YamlDotNet config/type converters; search untrusted YAML upload.

Code minh họa: vì sao lỗi và hướng sửa
// ✅ deserialize to explicit DTO; deny arbitrary tags/types
Phòng tránh / production: Typed schema/DTO; safe deserializer config; reject unknown tags; patch dependencies.

G. File Operations

Path Traversal

Critical · CWE-22

Khi nào bị?

Ghép filename/path từ user vào filesystem path.

Ví dụ thực tế

`GET /download?file=../../...` và `Path.Combine(root,file)` không đảm bảo path vẫn trong root.

Mức độ nguy hiểm

Đọc config/secret/source; nếu write thì có thể overwrite file.

Cách kiểm tra

Search `Path.Combine` với request input; test canonical path boundary.

Code minh họa: vì sao lỗi và hướng sửa
var full = Path.GetFullPath(Path.Combine(root, file));
if (!full.StartsWith(Path.GetFullPath(root), StringComparison.OrdinalIgnoreCase)) return BadRequest();
Phòng tránh / production: Server-generated IDs; canonicalize + root boundary; allow-list names/extensions; least filesystem permissions.

Zip Slip

High · CWE-22

Khi nào bị?

Extract ZIP entries theo `entry.FullName` mà không check canonical path.

Ví dụ thực tế

Archive chứa entry path thoát khỏi extract directory.

Mức độ nguy hiểm

Overwrite file ngoài thư mục extract; có thể thành RCE nếu ghi vào executable/config/web root.

Cách kiểm tra

Review zip extraction loops; scan archive entry names.

Code minh họa: vì sao lỗi và hướng sửa
var dest = Path.GetFullPath(Path.Combine(extractRoot, entry.FullName));
if (!dest.StartsWith(rootFull)) reject;
Phòng tránh / production: Canonical path check từng entry; reject absolute/parent paths; size/count limits.

Arbitrary File Write

Critical · CWE-73

Khi nào bị?

User kiểm soát path/filename đích ghi file.

Ví dụ thực tế

Upload API cho `targetPath` tùy ý rồi `File.WriteAllBytes(targetPath, ...)`.

Mức độ nguy hiểm

Overwrite config/code/startup file, persistence/RCE tùy quyền.

Cách kiểm tra

Search write APIs với request path; file integrity monitoring.

Code minh họa: vì sao lỗi và hướng sửa
var safeName = Guid.NewGuid().ToString("N");
var path = Path.Combine(uploadRoot, safeName);
Phòng tránh / production: Server chooses path/name; upload outside web root; least OS permissions; immutable container filesystem nơi có thể.

H. Server-Side Request Forgery (SSRF)

Basic SSRF

Critical · CWE-918

Khi nào bị?

Backend fetch URL do user cung cấp.

Ví dụ thực tế

Image preview/webhook tester nhận URL và `HttpClient.GetAsync(url)`.

Mức độ nguy hiểm

Backend có thể truy cập internal services, metadata endpoint, localhost, private IP mà user không truy cập trực tiếp.

Cách kiểm tra

Log outbound destinations; egress monitoring; review URL-fetch features.

Code minh họa: vì sao lỗi và hướng sửa
// ✅ Prefer allow-listed hosts + DNS/IP validation + egress firewall
Phòng tránh / production: Allow-list scheme+host; resolve DNS và chặn private/link-local/loopback; disable redirects hoặc revalidate; egress network policy/firewall.

SSRF via File Upload

High · CWE-918

Khi nào bị?

Uploaded XML/SVG/document chứa external reference, parser/converter tự fetch URL.

Ví dụ thực tế

SVG/XML processor tải external image/schema/font.

Mức độ nguy hiểm

SSRF gián tiếp, metadata/internal service access.

Cách kiểm tra

Review document converters/parsers; outbound calls từ worker.

Code minh họa: vì sao lỗi và hướng sửa
// ✅ parser resolver disabled; converter run in network-isolated worker
Phòng tránh / production: Disable external resource loading; sandbox processing; egress deny-by-default; file type validation.

I. Business Logic Flaws

Negative Quantities

Medium · CWE-20

Khi nào bị?

Chỉ validate kiểu dữ liệu mà không validate invariant nghiệp vụ.

Ví dụ thực tế

Order API cho quantity=-5 → total âm/stock tăng sai.

Mức độ nguy hiểm

Mất tiền, sai inventory/accounting; có thể không bị SAST phát hiện.

Cách kiểm tra

Boundary/abuse-case tests; anomaly detection totals âm.

Code minh họa: vì sao lỗi và hướng sửa
if (request.Quantity <= 0 || request.Quantity > 1000) return ValidationProblem();
Phòng tránh / production: Domain validation server-side; DB constraints nơi phù hợp; không tin UI validation.

Mass Assignment

High · CWE-915

Khi nào bị?

Bind request trực tiếp vào entity có field nhạy cảm.

Ví dụ thực tế

`UpdateUser(User entity)` cho phép client gửi Role/IsApproved/CreditLimit.

Mức độ nguy hiểm

Privilege escalation/data tampering.

Cách kiểm tra

Fuzz request với extra fields; review controller actions.

Code minh họa: vì sao lỗi và hướng sửa
public record UpdateUserRequest(string DisplayName, string Phone);
Phòng tránh / production: Dedicated DTO/commands; explicit mapping; reject/ignore unknown sensitive fields.

Integer Overflow

Medium · CWE-190

Khi nào bị?

Phép toán integral overflow làm wrap/truncate, nhất là quantity*price/size.

Ví dụ thực tế

`int totalBytes = count * itemSize`; giá trị lớn overflow thành số nhỏ và bypass limit.

Mức độ nguy hiểm

Bypass limit, sai tiền/số lượng, exception/DoS.

Cách kiểm tra

Boundary tests MaxValue; analyzers.

Code minh họa: vì sao lỗi và hướng sửa
checked { var total = count * itemSize; }
// hoặc dùng long/decimal đúng domain
Phòng tránh / production: `checked`, proper numeric type, upper/lower bounds trước phép toán.

J. API Security

Missing Rate Limiting

High · CWE-799

Khi nào bị?

Endpoint login/search/export/expensive API không giới hạn tần suất.

Ví dụ thực tế

Một client gọi hàng nghìn request/s làm CPU/DB hoặc provider cạn quota.

Mức độ nguy hiểm

DoS, brute force/password spraying, chi phí cloud tăng.

Cách kiểm tra

RPS per principal/IP, 429 metrics, saturation dashboard.

Code minh họa: vì sao lỗi và hướng sửa
builder.Services.AddRateLimiter(...); // policy theo IP/user/API key + downstream capacity
Phòng tránh / production: ASP.NET rate limiter/APIM/App Gateway; per-user/IP/token buckets; quota; backpressure.

Excessive Data Exposure

Medium · CWE-213

Khi nào bị?

API trả entity đầy đủ và kỳ vọng UI tự bỏ field không cần.

Ví dụ thực tế

`GET /users` serialize entity gồm Email, InternalNotes, PasswordHash.

Mức độ nguy hiểm

Rò PII/secret/internal metadata; frontend bug/log có thể expose.

Cách kiểm tra

Inspect JSON contracts; snapshot tests; DLP.

Code minh họa: vì sao lỗi và hướng sửa
return Ok(users.Select(x => new UserDto(x.Id, x.DisplayName)));
Phòng tránh / production: Response DTO/projection; data minimization; field-level auth khi cần.

CORS Misconfiguration

High · CWE-942

Khi nào bị?

Cho origin quá rộng, đặc biệt credentials + untrusted origin.

Ví dụ thực tế

Policy reflect lại bất kỳ `Origin` rồi `AllowCredentials`.

Mức độ nguy hiểm

Website attacker có thể đọc response bằng browser với credential nếu policy sai.

Cách kiểm tra

Inspect response `Access-Control-Allow-Origin/Credentials`; test origins.

Code minh họa: vì sao lỗi và hướng sửa
builder.Services.AddCors(o => o.AddPolicy("spa", p => p.WithOrigins("https://app.company.com").AllowAnyHeader().AllowAnyMethod().AllowCredentials()));
Phòng tránh / production: Exact origin allow-list; không dùng wildcard với credentials; CORS không thay thế authorization.

CSRF (Cross-Site Request Forgery)

High · CWE-352

Khi nào bị?

Browser tự gửi cookie auth cho cross-site request và server không có anti-CSRF defense.

Ví dụ thực tế

App MVC cookie-auth có POST `/transfer` không antiforgery; attacker lừa browser user submit form.

Mức độ nguy hiểm

Thực hiện action dưới identity nạn nhân. Bearer token trong Authorization header ít bị CSRF hơn nếu token không tự attach cross-site.

Cách kiểm tra

Review state-changing cookie-auth endpoints; SameSite behavior.

Code minh họa: vì sao lỗi và hướng sửa
[ValidateAntiForgeryToken]
[HttpPost]
public IActionResult Update(...) { ... }
Phòng tránh / production: Antiforgery token; SameSite cookies; Origin/Referer checks defense-in-depth; không dùng GET cho state change.
